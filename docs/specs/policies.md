## 1. 인증·인가 정책

### 1.1 회원 정책

이 서비스는 **일반 사용자를 받지 않는 내부 관제 도구**다. 회원가입·이메일·탈퇴 개념이 없으며, 시드로 생성한 계정으로만 로그인한다(기획서 5.3 범위 외 기능).

| 항목 | 정책 |
| --- | --- |
| 가입 방법 | **없음.** 시드 스크립트로 관리자 계정만 생성한다 |
| 이메일 인증 | 없음 — 이메일을 수집하지 않는다 |
| 닉네임 규칙 | `users.display_name` 선택 입력, 최대 100자, 중복 허용 |
| 아이디 규칙 | `users.username` 영문 소문자·숫자·`_`, 3~50자, 중복 불가 |
| 비밀번호 규칙 | 최소 12자. 해시는 **argon2id** (bcrypt 아님 — 1.4 참조) |
| 탈퇴 방식 | 없음. 계정 회수는 `users.disabled_at`을 채우는 비활성화로 처리 |
| 개인정보 마스킹 | 해당 없음 — 개인정보를 저장하지 않는다. 단 `traces.question`·`answer`에 최종 사용자 입력이 담기므로 7장 보관 정책을 적용한다 |
| 계정 잠금 | 로그인 실패 **5회** 시 **10분** 잠금. 애플리케이션 메모리에서 IP+아이디 단위로 집계하며 DB 테이블은 두지 않는다 |

계정 잠금을 메모리로 처리하는 이유는 서버가 한 대이고 계정도 하나이기 때문이다. 서버가 늘어나면 공유 저장소가 필요하므로 그때 재검토한다(미결정).

### 1.2 토큰 정책

**Access/Refresh 토큰 구조를 쓰지 않는다.** 서버 세션 + httpOnly 쿠키 단일 토큰 방식이다(ADR-017). 세션 기준으로 정의한다.

| 항목 | 값 | 비고 |
| --- | --- | --- |
| Access Token TTL | **해당 없음** | JWT 미사용 |
| Refresh Token TTL | **해당 없음** | 재발급 개념 없음 |
| 세션 토큰 TTL | **24시간** | 만료 시 재로그인. 연장(슬라이딩) 없음 |
| 세션 토큰 저장 | 쿠키에 원문, DB에는 **SHA-256 해시만** | DB 유출 시에도 세션 탈취 불가 |
| 쿠키 속성 | `httpOnly`, `Secure`, `SameSite=Lax`, `Path=/` | 프론트와 API가 같은 출처이므로 `SameSite=None` 불필요 (ADR-018) |
| 다중 기기 로그인 | **허용.** 기기 수 제한 없음 | 사용자가 사실상 1명이라 제한 실익이 없다 |
| 강제 로그아웃 | 비밀번호 변경·계정 비활성화 시 해당 사용자의 **전체 세션 즉시 폐기**(`revoked_at` 기록) | 즉시 무효화가 세션 방식을 택한 이유다 |
| 세션 검증 조건 | `token_hash` 일치 **AND** `expires_at > now()` **AND** `revoked_at IS NULL` | 세 조건 모두 만족해야 통과 |

### 1.3 권한 정책

콘솔은 역할 등급을 두지 않고 **로그인 여부만** 구분한다(기획서 3.3). 다만 시스템에는 사람 외의 접근 주체가 더 있으므로 **주체(Principal)** 단위로 권한을 정의한다.

| 주체 | 설명 | 부여 방법 | 권한 범위 |
| --- | --- | --- | --- |
| `GUEST` | 비로그인 | — | 로그인 엔드포인트와 헬스체크만. 그 외 전부 401 |
| `OPERATOR` | 로그인한 콘솔 사용자 | 시드 계정으로 로그인 | 전 화면 조회 + 라우팅 정책 적용·알림 설정 저장(쓰기) |
| `COLLECTOR` | 계측 데이터를 보내는 SDK/Collector | 내부 네트워크 접근만 허용 | Ingest API `POST`만. 조회 불가 |
| `WORKER` | 검사 워커·Drift Monitor·에이전트 호출 코드 | 서버 내부 프로세스 | DB 읽기·쓰기 전체 |
| `AGENT` | 원인 분석 에이전트(MCP 도구) | **DB read-only 계정** | `SELECT`만. INSERT/UPDATE/DELETE 불가 (ADR-007) |
- `OPERATOR`의 쓰기 행위는 그 자체가 "변경"이므로 `version_changes`에 `source='console'`로 기록한다(ADR-005).
- `AGENT`의 권한 제한은 애플리케이션 로직이 아니라 **DB 계정 권한**으로 강제한다. 코드 버그가 있어도 쓰기가 불가능해야 한다.
- 역할 매트릭스는 API 명세서의 권한 표와 일치시킨다. 역할이 늘어나면 두 문서를 같은 PR에서 고친다.

## 2. 시간·TTL 정책

### 2.1 TTL 표

| 항목 | TTL | 만료 시 동작 |
| --- | --- | --- |
| 세션 토큰 | **24시간** | 401 반환 → 재로그인 |
| 로그인 잠금 | **10분** | 잠금 해제, 실패 카운터 초기화 |
| 검사 작업 점유(stale lock) | **5분** | `RUNNING` → `PENDING` 복귀, `attempts` 증가 |
| 검사 작업 재시도 백오프 | **2s → 8s → 32s** | `available_at` 갱신 후 재대기 |
| 검사 배치 대기(T) | **2초** (또는 N=16건) | 먼저 도달한 조건에서 배치 추론 실행 |
| 드리프트 판정 창 | **5분** (비교 변수: 15분, N건) | 창 종료 시 집계·판정 후 `quality_windows` 기록. **창 배분 기준은 `traces.started_at`** |
| 알림 재발송 쿨다운 | **30분** | 동일 `dedup_key` 알림 억제 |
| 인시던트 자동 종료 | **연속 2개 창 정상** | `status` → `RESOLVED` |
| 에이전트 조사 제한 | 호출 **12회** 또는 토큰 **60,000** | 규칙 기반 결과로 대체(`agent_fallback=true`) |
| LLM 호출 타임아웃 | **60초** (2단계 채점·에이전트), **30초** (RAG 생성) | 재시도 → 실패 처리 |
| Batch API 대기 상한 | **24시간** | 미완료 배치는 실패 처리 후 보고 |
| 주입 실험 1회차 | 시나리오 정의값 (기본 **90분**, 주입 시점 30분) | `status` → `COMPLETED` |
| OTLP 배치 전송 주기 | **5초** 또는 큐 512건 | 비동기 전송, 실패 시 드롭 |
- 세션 TTL 24시간은 실습·시연 기간을 한 번에 덮을 수 있는 길이로 잡았다.
- 배치 대기 2초와 드리프트 창 5분은 **실험으로 조정되는 값**이다. 변경 시 이 표와 `configs/`를 함께 고친다.
- 스테일 락 TTL(5분)은 LLM 호출 타임아웃(최대 60초)보다 충분히 길어야 정상 처리 중인 작업을 회수하지 않는다(2.2 불변식 참조).

### 2.2 불변식

시간과 관련해 항상 참이어야 하는 조건이다. 위반은 버그로 간주한다.

```
[항상 참] traces.started_at <= traces.ended_at
[항상 참] traces.ended_at <= traces.created_at            -- 수집은 요청 종료 이후에 일어난다
[항상 참] quality_windows.window_start < window_end
[항상 참] window_end - window_start = window_size_sec
[항상 참] quality_windows 집계 기준 = traces.started_at  -- evaluations.created_at 아님 (erd.md 1장 원칙)
[항상 참] incidents.estimated_start_at <= incidents.detected_at
[항상 참] incidents.detected_at <= incidents.resolved_at  -- resolved_at이 있을 때
[항상 참] sessions.created_at < sessions.expires_at
[항상 참] eval_jobs.available_at >= eval_jobs.created_at
[항상 참] injection_events.applied_at >= injection_runs.started_at   -- applied_at이 있을 때
[항상 참] injection_events.applied_at <= injection_runs.ended_at     -- 둘 다 있을 때
[항상 참] version_changes.changed_at >= versions.created_at (to_version 기준)
[항상 참] 배치 대기 T < 드리프트 판정 창                  -- 창 집계 시점에 검사가 끝나 있어야 한다
[항상 참] 알림 쿨다운 >= 드리프트 판정 창                 -- 창마다 알림이 나가면 폭주한다
[항상 참] stale lock TTL > LLM 호출 타임아웃              -- 정상 처리 중인 작업을 회수하면 안 된다
[항상 참] 모든 TIMESTAMPTZ는 UTC로 저장된다
```

아래 세 줄은 DB 제약으로 표현할 수 없는 **설정값 사이의 관계**다. 애플리케이션 기동 시 설정 검증 단계에서 확인하고, 위반 시 기동을 중단한다.

- `배치 대기 T(초) < 드리프트 판정 창(초)` (기본값 2 < 300)
- `알림 쿨다운(초) >= 드리프트 판정 창(초)` (기본값 1800 >= 300)
- `stale lock TTL(초) > LLM 호출 타임아웃(초)` (기본값 300 > 60)

### 2.3 세션·상태 복구 정책

| 이탈 구간 | 복구 기준 | 복구 방법 | 재진입 조건 |
| --- | --- | --- | --- |
| 세션 유효 (24시간 이내) | 세션 유지 | 그대로 진행 | — |
| 세션 만료 | 완전 만료 | 재로그인 요청 | 로그인 후 **이탈 전 화면 경로로 복귀** |
| 세션 폐기(`revoked_at`) | 강제 종료 | 재로그인 요청 | 로그인 후 대시보드로 이동 |
| 서버 재기동 | 세션 유지 | DB에 세션이 있으므로 영향 없음 | — |

**사람이 아닌 주체의 상태 복구**

| 이탈 구간 | 복구 기준 | 복구 방법 |
| --- | --- | --- |
| 워커 비정상 종료 | `locked_at`이 5분 경과 | 스케줄러가 `PENDING`으로 되돌리고 `attempts` 증가 |
| Collector 중단 | 수집만 중단 | **RAG 서비스는 정상 동작.** 복구 후 신규 요청부터 다시 수집 |
| DB 재기동 | 커넥션 끊김 | 애플리케이션이 재연결. 미커밋 트랜잭션은 롤백 |
| 에이전트 중단 | 인시던트가 `INVESTIGATING`에 머묾 | 스케줄러가 30분 초과 시 `agent_fallback=true`로 규칙 기반 결과를 채우고 종료 |
| 주입 실험 중단 | 트래픽·주입 정지 | 회차를 `ABORTED`로 표시. **해당 회차 데이터는 지표에서 제외**하고 재실행 |

## 3. 비즈니스 규칙

DB 제약이나 코드 조건으로 보장해야 하는 핵심 규칙이다. 구현 방법이 아니라 규칙 자체를 기술한다.

### 3.1 수집 (Ingest)

- 트레이스 저장과 검사 작업 등록은 **같은 트랜잭션**에서만 일어난다(ADR-004).
- 같은 `trace_id`가 다시 들어오면 **무시한다**(멱등). 재전송이 중복 검사를 만들지 않는다.
- 수집 실패는 감시 대상 서비스의 응답에 영향을 주지 않는다. SDK는 전송 실패를 삼킨다.
- 버전 3종(`prompt`, `model`, `retrieval`)이 모두 연결된 트레이스만 **원인 분석과 A/B 비교의 모집단**이다.
- 응답이 없는 트레이스(`status='ERROR'`)는 검사 작업을 등록하지 않는다.

### 3.2 품질 검사 (1·2단계)

- **모든 트레이스는 1단계 검사를 거친다.** 미검사 트레이스는 0건이어야 한다.
- **1단계 `score`는 환각 의심 점수**(높을수록 환각 가능성 높음). **2단계 `score`는 품질 점수**(높을수록 좋음). 라우팅 임계값 `τ`는 1단계 점수에 적용한다(`score >= τ`이면 2단계 전달). (erd.md 1장 점수 방향 원칙)
- 콘솔의 "품질 점수" 시계열은 stage 2 결과가 있으면 그 값, 없으면 `1 − stage_1_score`로 표시 레이어에서 변환한다.
- 2단계 평가는 같은 트레이스의 1단계 결과가 있을 때만 생성된다.
- 2단계 전달 조건은 `score >= τ`(사유 `threshold`) 또는 비율 `r` 무작위 추첨(사유 `sample`) 둘뿐이다.
- **무작위 표본 `r`은 비용이 아니라 측정 장치다.** `r = 0`으로 운영하면 누락률을 계산할 수 없으므로, 실험 구간에서 `r > 0`을 유지한다.
- 같은 평가자(`evaluator_key`)가 같은 트레이스를 두 번 채점하지 않는다. 평가자가 다르면 추가 채점은 허용된다(모델 비교·교차 검증).
- 검사 결과는 INSERT 후 수정하지 않는다. 재평가가 필요하면 새 평가자 키로 행을 추가한다.
- 1단계 비용은 0으로 기록한다(자체 CPU 추론). 비용 비교는 2단계 호출 비용만으로 계산한다.

### 3.3 버전·변경 이력

- 버전의 원본은 Git `configs/` 파일이다. 사람이 DB에 버전을 직접 만들지 않는다.
- 내용 해시가 직전 버전과 같으면 변경으로 기록하지 않는다. **동일 내용 재배포는 변경이 아니다.**
- 모든 변경은 출처(`deploy` / `injection` / `console`)가 반드시 하나 기록된다.
- 콘솔에서 라우팅 정책이나 알림 설정을 바꾸면 그 자체가 변경이므로 이력에 남고, 이후 품질 저하의 원인 후보에 포함된다.
- 변경 이력은 삭제하지 않는다. 잘못 기록된 변경도 취소 변경을 추가로 기록해 표현한다.

### 3.4 드리프트 감지

- **창 집계는 `traces.started_at` 기준**으로 수행한다. `evaluations.created_at`이나 `embeddings.created_at`을 기준으로 삼지 않는다(erd.md 1장 창 집계 기준 원칙, ADR-029).
- 시간 창의 표본 수가 **30건 미만이면 판정을 보류**한다. 집계 행은 남기되 `is_drift=false`, `drift_score=NULL`로 기록한다.
- 판정기 3종은 같은 창에 대해 **각각 독립적으로** 판정하고 모두 기록된다. 한 판정기의 결과가 다른 판정기를 덮지 않는다.
- 인시던트를 만드는 판정기는 **설정으로 지정된 1종**이다. 나머지 2종은 기록만 한다.
- 같은 지표·판정기로 열린 인시던트가 이미 있으면 새 인시던트를 만들지 않는다.
- 연속 2개 창이 정상이면 인시던트를 자동 `RESOLVED`로 바꾼다.
- `quality_windows.mean_score`는 표시 레이어 변환(`stage 2 있으면 그 값, 없으면 1 − stage_1_score`)을 이미 적용한 값을 저장한다.

#### baseline 구간 선택 기준

`DriftDetector.judge`의 `baseline` 인자를 구성하는 책임은 호출자(Drift Monitor)에 있다.
아래 규칙에 따라 baseline 창 목록을 선택한다.

- **baseline 창 수**: 최근 정상 창 **12개**를 기본으로 사용한다 (5분 창 기준 1시간). 주입 실험 시간 창을 조정할 경우 이 값도 비례하여 조정한다.
- **초기 기동**: baseline 창이 12개 미만이면 `DriftDetector`가 `deferred=True`를 반환한다. Drift Monitor는 이를 판정 보류로 처리하고 창을 쌓을 때까지 기다린다.
- **인시던트 발생 구간 제외**: `is_drift=true`로 판정된 창과 `OPEN` / `INVESTIGATING` 인시던트가 열린 구간의 창은 baseline에 포함하지 않는다. 저하 구간이 baseline에 섞이면 다음 저하를 탐지하지 못한다.
- **baseline 갱신 시점**: 인시던트가 `RESOLVED`로 전환된 직후, 해당 인시던트 구간을 제외한 최근 정상 창 12개로 baseline을 재구성한다.
- **baseline 저장**: Drift Monitor는 baseline 창 목록을 별도로 저장하지 않는다. 판정 시점에 `quality_windows` 테이블에서 조건(`is_drift=false`, `deferred=false`, 최근 12개)으로 조회한다.

### 3.5 원인 분석 에이전트

- 에이전트는 **조회만 한다.** 롤백·설정 변경·알림 발송 등 상태를 바꾸는 동작을 수행하지 않는다.
- 조사 대상 기간은 `estimated_start_at` 기준 **직전 24시간**으로 제한한다.
- 호출 12회 또는 토큰 60,000을 넘으면 즉시 중단하고 규칙 기반 결과(직전 변경 지목)로 대체한다.
- 결론은 정해진 JSON 구조여야 한다. 검증 실패 시 1회 재시도하고, 그래도 실패하면 폴백한다.
- `agent_result`의 1순위 후보와 `top1_version_change_id`는 항상 일치한다.
- 폴백으로 만들어진 결과(`agent_fallback=true`)는 **에이전트 성능 집계에서 제외**한다.
- 모든 도구 호출은 `agent_steps`에 순서대로 남는다.

### 3.6 알림

- 하나의 인시던트는 채널당 **1회만** 알린다.
- 동일 `dedup_key`(지표+판정기+시간 버킷)는 쿨다운 30분 동안 억제한다.
- 알림 본문에는 하락 시점, 원인 후보 1순위, 근거 요약, 콘솔 링크가 포함된다.
- 발송 실패는 재시도하되, 최종 실패해도 인시던트 처리 흐름을 막지 않는다.
- 발송한 메시지 본문은 스냅샷으로 저장한다.

### 3.7 주입 실험

- 주입 내역이 곧 정답 라벨이다. 주입으로 생긴 변경은 반드시 `injection_events`와 연결된다.
- 디코이 변경(`is_decoy=true`)은 정답이 아니다. 정확도 계산에서 `is_decoy=false`인 이벤트만 대상으로 한다.
- 주입이 실패한 회차는 `ABORTED`로 표시하고 **해당 회차 전체를 지표에서 제외**한다.
- 같은 시드로 재실행하면 질문 순서와 주입 시점이 재현된다.
- 시연 모드(`demo`) 회차는 실험 지표 집계에 포함하지 않는다.
- 실험 구간 중에는 집계에 쓰이는 스키마와 지표 계산식을 변경하지 않는다.

### 3.8 비용

- 요청·검사 1건의 비용은 **SDK 내부 단가표**로 계산해 기록한다(ADR-025).
- 단가표는 버전(`kind='pricing'`)으로 기록되며, 단가가 바뀌면 그 시점 이후 요청에만 적용된다. **과거 기록은 소급 수정하지 않는다.**
- Batch API 할인(50%)과 캐시 적중은 계산에 반영한다.
- 지출 한도에 도달하면 2단계 채점을 중단하고 1단계 결과만 유지한다. 서비스 전체를 멈추지 않는다.

### 3.9 계정·세션

- 비활성화된 계정의 세션은 즉시 전부 폐기한다.
- 비밀번호 변경 시 해당 사용자의 모든 세션을 폐기한다.
- 세션 토큰 원문은 서버 어디에도 저장하지 않는다.

## 4. 주요 상태 전이

상태를 가지는 도메인 객체의 상태 머신이다. DB 설계 문서(erd.md 8장)의 코드값 정의와 일치해야 한다.

### 검사 작업 (`eval_jobs`)

| 현재 상태 | 트리거 | 다음 상태 | 전이 조건 |
| --- | --- | --- | --- |
| — | 트레이스 저장 | `PENDING` | 트레이스 INSERT와 **같은 트랜잭션** |
| `PENDING` | 워커 점유 | `RUNNING` | `available_at <= now()`, `SKIP LOCKED`로 선점 |
| `RUNNING` | 검사 완료 | `DONE` | 1단계(및 필요 시 2단계) 결과 INSERT 성공 |
| `RUNNING` | 검사 실패 | `PENDING` | `attempts < 3` — 백오프 후 재대기 |
| `RUNNING` | 재시도 상한 초과 | `FAILED` | `attempts >= 3` |
| `RUNNING` | 점유 5분 경과(워커 사망) | `PENDING` | stale lock 회수, `attempts` 증가 |

```
stateDiagram-v2
    [*] --> PENDING : 트레이스 저장(동일 트랜잭션)
    PENDING --> RUNNING : 워커 점유(SKIP LOCKED)
    RUNNING --> DONE : 검사 결과 저장 성공
    RUNNING --> PENDING : 실패 후 백오프 (attempts < 3)
    RUNNING --> PENDING : stale lock 회수 (5분 경과)
    RUNNING --> FAILED : 재시도 상한 초과
    DONE --> [*]
    FAILED --> [*]
```

### 인시던트 (`incidents`)

| 현재 상태 | 트리거 | 다음 상태 | 전이 조건 |
| --- | --- | --- | --- |
| — | 드리프트 판정 | `OPEN` | 같은 지표·판정기로 열린 인시던트가 없을 때만 |
| `OPEN` | 에이전트 호출 | `INVESTIGATING` | 에이전트 루프 시작 |
| `INVESTIGATING` | 결론 저장 | `RESOLVED` | 구조화 JSON 검증 통과, `top1_version_change_id` 기록 |
| `INVESTIGATING` | 상한 도달·조사 실패 | `RESOLVED` | 규칙 기반 결과로 대체, `agent_fallback=true` |
| `INVESTIGATING` | 30분 경과(에이전트 중단) | `RESOLVED` | 스케줄러가 폴백 처리 |
| `OPEN` / `INVESTIGATING` | 연속 2개 창 정상 | `RESOLVED` | 품질 자동 회복 |
| `OPEN` / `INVESTIGATING` | 표본 부족 확인·운영자 판단 | `DISMISSED` | 오탐으로 종료 — **오탐 횟수 집계에 포함** |

```
stateDiagram-v2
    [*] --> OPEN : 드리프트 판정
    OPEN --> INVESTIGATING : 에이전트 조사 시작
    INVESTIGATING --> RESOLVED : 원인 후보 + 근거 저장
    INVESTIGATING --> RESOLVED : 상한 도달 → 규칙 기반 대체
    OPEN --> RESOLVED : 연속 2개 창 정상
    OPEN --> DISMISSED : 오탐 판단
    INVESTIGATING --> DISMISSED : 오탐 판단
    RESOLVED --> [*]
    DISMISSED --> [*]
```

## 6. 에러·재시도 정책

### 6.1 재시도 규칙

| 대상 | 재시도 대상 | 최대 횟수 | 백오프 | 재시도 제외 |
| --- | --- | --- | --- | --- |
| LLM API (2단계 채점·에이전트) | 429, 5xx, 타임아웃, 연결 오류 | **3회** | 1s → 4s → 16s (지터 ±20%) | 400, 401, 403 |
| LLM API (RAG 생성) | 429, 5xx, 타임아웃 | **2회** | 1s → 3s | 4xx. 실패 시 `traces.status='ERROR'` |
| Slack Webhook | 429, 5xx, 타임아웃 | **3회** | 1s → 5s → 25s | 400, 404 |
| 검사 작업 (`eval_jobs`) | 워커 예외, 추론 실패 | **3회** | 2s → 8s → 32s | 입력 검증 실패(즉시 `FAILED`) |
| DB 커넥션 | 연결 끊김, 일시적 오류 | **3회** | 0.5s → 1s → 2s | 제약 위반(즉시 실패) |
| OTLP 전송 (SDK) | 전송 실패 | **2회** | 1s → 3s | 그 외 — **실패 시 드롭.** 서비스 응답을 막지 않는 것이 우선 |
| Batch API 결과 조회 | 미완료 상태 | 24시간 내 폴링 | 1분 간격 | 상한 초과 시 실패 처리 |
- 재시도에 지터를 넣는 이유는 다수 작업이 동시에 실패했을 때 같은 시점에 몰려 재시도하는 것을 피하기 위해서다.
- 재시도 가능 여부 판단은 **상태 코드 기준**으로만 한다.

### 6.2 Fallback 동작

| 장애 상황 | Fallback 동작 |
| --- | --- |
| LLM API 전체 다운 | 2단계 채점 중단, **1단계 결과만으로 운영 계속.** 해당 구간은 2단계 표본이 없음을 지표 보고에 명시 |
| LLM 지출 한도 도달 | 2단계 채점 일시 중단, 1단계 유지. 콘솔에 경고 표시 |
| 1단계 탐지 모델 로딩 실패 | 작업을 재시도 큐에 남기고 경보. **트레이스 수집은 계속**(사후 재검사 가능) |
| 에이전트 상한 도달·오류 | **규칙 기반 원인 지목**(직전 변경)으로 대체, `agent_fallback=true` |
| Slack 발송 실패 | 인시던트는 정상 생성·기록. 콘솔에서 확인 가능하며 발송 실패를 표시 |
| Collector 중단 | SDK가 전송 실패를 드롭. **RAG 서비스 정상 동작.** 복구 후 신규 요청부터 재수집 |
| DB 다운 | 수집·검사 전면 중단. RAG 서비스는 계속 동작(계측만 실패) |
| 임베딩 모델 실패 | 품질 점수 기반 드리프트 판정만 수행, 임베딩 거리 판정은 건너뜀 |
| Grafana 임베드 실패 | 콘솔의 해당 패널만 비우고 나머지 화면은 정상 표시 |
| 주입 실패 | 회차 `ABORTED`, 데이터 폐기 후 재실행 |

모든 Fallback의 공통 원칙은 **"감시가 감시 대상을 멈추지 않는다"** 이다.

### 6.3 에러 응답 규약

| 상황 | HTTP 상태 | 본문 |
| --- | --- | --- |
| 비로그인 접근 | 401 | `{"error": "UNAUTHORIZED"}` |
| 세션 만료 | 401 | `{"error": "SESSION_EXPIRED"}` — 프론트는 로그인 화면으로 이동 |
| 입력 검증 실패 | 400 | 필드별 오류 목록 |
| 리소스 없음 | 404 | `{"error": "NOT_FOUND"}` |
| 중복 생성(멱등 위반) | 409 | 기존 리소스 식별자 반환 |
| 서버 오류 | 500 | 상세 메시지 **미노출**, 서버 로그에 trace id 기록 |

에러 응답에 내부 예외 메시지나 SQL을 노출하지 않는다.

## 7. 데이터 보관·삭제 정책

| 데이터 | 보관 기간 | 삭제 방식 |
| --- | --- | --- |
| 사용자 계정 | 무기한 (계정 1개) | 회수 시 `disabled_at` 비활성화. 물리 삭제 없음 |
| 세션 | 만료 후 **7일** | 배치로 물리 삭제 |
| 트레이스·스팬 | **논문 투고 완료까지** | 기간 종료 후 `injection_runs` 단위로 일괄 삭제 |
| 검사 결과 (`evaluations`) | **영구 보존** | 삭제하지 않음 |
| 품질 창·인시던트·조사 과정 | **영구 보존** | 삭제하지 않음 |
| 버전·변경 이력 | **영구 보존** | 삭제하지 않음 |
| 임베딩 | 트레이스와 동일 | 트레이스 삭제 시 함께 삭제 |
| 알림 이력 | **영구 보존** | 삭제하지 않음 |
| 애플리케이션 로그 | **14일** | 물리 삭제 |
| Prometheus 메트릭 | **15일** | retention 설정으로 자동 삭제 |
| 시연용 코퍼스 트레이스 | 시연 종료 후 삭제 가능 | `mode='demo'` 회차 단위 삭제 |

**삭제 시 규칙**

- 트레이스를 지울 때는 `injection_runs` 회차 전체를 함께 지운다.
- FK가 `RESTRICT`이므로 삭제 순서는 `embeddings` → `evaluations` → `eval_jobs` → `spans` → `traces` 순이다.
- `evaluations`를 지우면 비용 절감률·누락률을 다시 계산할 수 없다. 용량이 부족하면 **`spans` → `traces.contexts` → `traces` 본문** 순으로 줄인다.
- 서버 종료(`terraform destroy`) 전에는 DB를 덤프해 보관한다.

## 9. 실험 데이터 유효성 정책

### 9.1 집계 포함 조건

| 지표 | 포함 조건 |
| --- | --- |
| 2단 구조 비용·누락률 | `evaluations` 전체. 단 실험 구간과 일반 구간을 분리 보고 |
| 드리프트 탐지율·탐지 지연 | `mode='experiment'`, `status='COMPLETED'` 회차만. **탐지 지연 = `incidents.detected_at` − `injection_events.applied_at`** |
| 오탐 횟수 | 주입이 없는 정상 구간에서 `is_drift=true`로 판정된 창 수 + `DISMISSED` 인시던트 |
| 원인 지목 정확도 | `agent_fallback=false`인 인시던트 × `is_decoy=false`인 주입 이벤트 |
| 탐지 모델 F1·지연 | 실험 스크립트의 평가 분할 결과. 서비스 DB와 분리 |
| 계측 오버헤드 | 부하 테스트 전용 구간. 실험 트래픽과 섞지 않음 |

### 9.2 제외 조건

- `injection_runs.status='ABORTED'` 회차의 모든 데이터
- `mode='demo'` 회차 (시연용)
- `agent_fallback=true`인 인시던트 (에이전트 성능 집계에서만 제외, 탐지 지표에는 포함)
- 표본 30건 미만으로 판정 보류된 창 (탐지율 분모에서 제외하되 보류 횟수를 함께 보고)
- 시연용 코퍼스로 생성된 트레이스
- 스키마·지표 계산식이 변경된 시점 전후가 섞인 구간

### 9.3 재현성 규칙

- 모든 실험은 시드, 질문 집합, 모델·프롬프트 버전, 판정기 설정을 파일로 고정하고 결과에 함께 기록한다.
- 결과표와 그래프는 저장소의 실험 코드에서 **자동 생성**한다.
- 측정은 시드를 바꿔 **3회 이상 반복**하고 평균과 편차를 함께 보고한다.
- 지연 측정은 예열 후 수행하고, 측정 환경(인스턴스 타입·vCPU·동시 실행 여부)을 함께 기록한다.
- **조건 없는 수치는 쓰지 않는다.**
