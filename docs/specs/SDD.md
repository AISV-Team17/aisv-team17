## 1. 기능 명세

기능 명세 형식: 문제 → 동작 방식 → 입출력 → 예외 상황 → 인수 기준. 설계 결정 근거는 관련 ADR을 참조한다.

### 1.1 계측 SDK와 버전 이력 관리

**문제:** 품질 저하의 원인이 "변경"인데, 요청 기록에 어떤 버전이었는지가 없으면 사후에 원인을 좁힐 수 없다.

**동작 방식**

데코레이터가 LLM 호출 구간을 스팬으로 감싸 표준 속성(`gen_ai.*`)과 자체 속성(`app.version.*`, `app.cost.usd`)을 기록하고, `BatchSpanProcessor`로 비동기 전송한다. 서비스 기동 시 `configs/` 각 파일의 내용 해시를 계산해 `versions`에 등록하고, 직전과 다르면 `version_changes`에 남긴다.

```python
# 사용 예시: 데코레이터 한 줄로 LLM 호출을 계측한다
@trace_llm(operation="chat")
def generate(question: str, ctx: VersionContext):
    ...
# 기록 속성 예
#  gen_ai.provider.name="anthropic"
#  gen_ai.request.model="claude-haiku-..."
#  gen_ai.usage.input_tokens=3104, gen_ai.usage.output_tokens=287   ← OTel 표준
#  app.version.prompt="v1.3", app.version.retrieval="topk5-chunk512" ← 자체 확장
#  app.cost.usd=0.0019                                               ← 단가표 기반
```

**입력 데이터:** 질문, 검색 문맥, 응답, 토큰 수, 모델명, 요청 시점의 버전 묶음.

**출력 데이터:** OTLP 스팬(트레이스), `versions` 레코드, `version_changes` 레코드.

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| 수집 경로 장애 | 전송 실패를 삼키고 서비스 응답은 정상 반환 |
| 버전 파일 파싱 실패 | **기동 중단** — 잘못된 버전으로 데이터를 더럽히지 않는다 |
| 동일 내용 재배포 | 해시가 같으므로 `version_changes` 미기록 |

**관련 ADR:** ADR-001 (SDK 방식), ADR-002 (OTel 버전 고정), ADR-005 (Git 원본 + DB 레지스트리)

**인수 기준**

- 데코레이터 적용만으로 트레이스가 콘솔에 보이고, 각 트레이스에 세 종류 버전 ID가 모두 연결된다.
- 계측 적용/미적용 p95 지연 차이를 수치로 보고할 수 있다.
- `configs/` 파일 1바이트 변경이 `version_changes` 1건으로 기록되고, 동일 내용 재배포는 기록되지 않는다.

### 1.2 1단계 경량 환각 탐지

**문제:** 모든 응답을 LLM으로 채점하면 비용이 서비스 운영 비용에 준한다. 그렇다고 표본만 보면 표본 사이의 저하를 놓친다.

**동작 방식**

문맥·질문·답변을 이어 붙여 토큰 분류 모델에 넣고, 근거로 뒷받침되지 않는 토큰 구간과 응답 단위 점수를 얻는다. ONNX·INT8로 변환해 CPU에서 배치 추론한다. 결과는 `evaluations`(stage=1)에 저장된다.

- **모델 선택:** 자체 미세조정 인코더(ModernBERT/DeBERTa-v3 계열, RAGTruth 학습). 학습 완료 전에는 LettuceDetect를 기준선 겸 임시 모델로 사용한다(ADR-027).
- **개선 축:** 추론 효율(크기·지연). 정확도–효율 곡선으로 결과 제시(ADR-028).
- **score 방향:** 0.0(clean) → 1.0(likely hallucinated). 높을수록 의심. `erd.md` 1장 점수 방향 원칙 참조.
- **구현 인터페이스:** `interfaces.md` `Detector` 참조.

**입력 데이터:** `EvalInput` (검색 문맥, 질문, 응답 텍스트).

**출력 데이터:** `DetectionResult` (응답 단위 의심 점수, 환각 의심 구간 목록).

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| 입력이 최대 길이 초과 | 문맥을 분할 처리. 예외를 던지지 않는다 |
| `contexts`가 빈 리스트 | 정상 처리. 높은 점수가 나오는 것이 기대 동작 |
| 모델 로딩 실패 | 해당 작업을 재시도 큐에 남기고 경보. **수집은 계속** |

**관련 ADR:** ADR-023 (ONNX 서빙), ADR-024 (Detector 인터페이스), ADR-027 (모델 선택), ADR-028 (개선 축)

**인수 기준**

- 모든 트레이스가 1단계 검사를 거친다. 미검사 트레이스 0건.
- EC2 t3.large CPU에서 배치 16건 기준 p95 지연과 처리량을 측정해 보고할 수 있다.
- LettuceDetect와 자체 모델을 같은 평가 코드에서 비교한 정확도–효율 곡선을 제시할 수 있다.

### 1.3 2단계 LLM 정밀 평가와 라우팅

**문제:** 경량 모델만으로는 판정 근거가 빈약하고, 1단계가 놓친 환각의 양을 알 수 없다.

**동작 방식**

`Router`가 `score >= τ`인 응답(사유: `threshold`)과 무작위 표본(사유: `sample`, 비율 `r`)을 2단계로 전달하고 사유를 `evaluations.routed_reason`에 기록한다. `Judge`가 근거 일치와 정확성을 채점하고 이유를 남긴다.

- **score 방향:** 0.0(bad) → 1.0(good). 높을수록 품질 좋음. stage 1과 방향 반대(`erd.md` 1장 점수 방향 원칙).
- **무작위 표본 `r`의 역할:** 비용이 아니라 **측정 장치**다. `r = 0`으로 운영하면 1단계 누락률을 추정할 방법이 사라진다.
- **라우팅 우선순위:** 임계값 판정이 표본 추첨보다 먼저다. 임계값으로 선택된 건은 표본 추첨 모집단에서 제외한다.
- **구현 인터페이스:** `interfaces.md` `Router`, `Judge` 참조.

**입력 데이터:** `DetectionResult` 목록, 정책(τ, r), `EvalInput` (Judge 입력용).

**출력 데이터:** `RoutingDecision` 목록, `JudgeResult` 목록. `evaluations`(stage=1,2)에 저장.

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| API 오류·429 | 지수 백오프 재시도(policies.md 6.1) |
| 지출 한도 도달 | 2단계를 일시 중단하고 1단계 결과만 유지 |
| 채점 결과 파싱 실패 | 1회 재시도 후 `JudgeParseError` |

**관련 ADR:** ADR-006 (비동기 워커), ADR-015 (LLM 단일 제공자 + 등급 분리), ADR-024 (인터페이스 계약), ADR-025 (비용 계산)

**인수 기준**

- `score >= τ`인 응답은 모두 2단계로 가고, 표본 비율이 설정값 `r`에 수렴하며 사유가 기록된다.
- τ·r 격자 실험에서 비용·누락률·정확도 유지율을 측정해 곡선으로 제시할 수 있다.
- LLM 단독 전수 채점 대비 비용 절감률을 수치로 보고할 수 있다.

### 1.4 채점자 신뢰도 검증

**문제:** LLM 채점 결과를 운영에 쓰기 전에 믿을 근거가 필요하다.

**동작 방식**

MT-Bench 사람 평가 데이터와 LLM 채점자 결과를 비교해 신뢰도를 측정한다. 측정 지표는 일치율, Cohen's kappa, 순서 교환 판정 유지율, 길이–승패 관계, 사람 간 일치율이다. 결과는 채점자 신뢰도 화면에 표시된다.

**편향 통제**

- **자기 선호 편향:** 생성(소형 모델)과 채점(중형 모델) 등급을 분리한다(ADR-015).
- **교차 검증:** 2단계 채점 결과 100~200건을 타 제공자 채점자로 재채점해 일치도를 보고한다.
- **채점자 자체 변동 분리:** `judge_prompt_version_id`로 채점 프롬프트 변경을 버전으로 추적한다(`erd.md` `versions.kind='judge_prompt'`).

**관련 ADR:** ADR-015 (LLM 등급 분리), ADR-028 (과제 B)

**인수 기준**

- MT-Bench 사람 평가와의 일치율·Cohen's kappa, 순서 교환 유지율, 사람 간 일치율을 함께 보고할 수 있다.
- 채점자 신뢰도 화면에서 혼동 행렬과 불일치 사례를 열람할 수 있다.

### 1.5 품질 드리프트 감지와 알림

**문제:** 점수가 쌓여도 사람이 그래프를 계속 보고 있을 수는 없다.

**동작 방식**

Drift Monitor(APScheduler)가 5분 창으로 품질 점수와 응답 임베딩 분포를 집계하고, 세 방식(`fixed_threshold`, `ks_test`, `embedding_distance`) 각각으로 저하를 판정한다(`DriftDetector` 인터페이스). 저하 감지 시 인시던트를 생성하고 에이전트를 호출한 뒤 Slack으로 보고한다.

- **창 집계 기준:** `traces.started_at` 기준으로 창을 배분한다(`erd.md` 1장 원칙).
- **콘솔 품질 점수:** stage 2 결과가 있으면 그 값, 없으면 `1 − stage_1_score`로 표시 레이어에서 변환한다(`erd.md` 1장 점수 방향 원칙).
- **판정 보류:** `sample_count < 30`이면 판정을 보류하고 집계 행은 남긴다.
- **알림 억제:** 인시던트당 채널당 1회, 동일 `dedup_key` 쿨다운 30분(policies.md 3.6).

**입력 데이터:** 시간 창별 품질 점수, 응답 임베딩(384차원), 직전 기준 구간.

**출력 데이터:** `quality_windows` 레코드, `incidents` 레코드, Slack 메시지.

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| 표본 부족(트래픽 희박) | 판정 보류(`DriftVerdict.deferred=True`), 창은 기록 |
| 같은 지표 재알림 | 쿨다운으로 억제 |
| 임베딩 모델 실패 | 점수 기반 판정만 수행, 임베딩 거리 판정 건너뜀 |

**관련 ADR:** ADR-024 (DriftDetector 인터페이스), ADR-029 (3방식 비교 실험)

**인수 기준**

- 주입 시나리오 5종에서 탐지율·탐지 지연·오탐 횟수를 방식별로 비교한 표를 낼 수 있다.
- 인시던트당 알림은 1회다. 연속 2개 창 정상이면 자동 RESOLVED된다.

### 1.6 원인 변경 탐지 에이전트

**문제:** 저하를 알아도 원인 변경을 찾는 데 시간이 걸린다. 후보가 여러 개면 사람이 하나씩 확인해야 한다.

**동작 방식**

인시던트 정보를 시작점으로, 조회 전용 MCP 도구를 반복 호출하며 조사하고, 원인 후보 순위·신뢰도·근거를 구조화된 JSON으로 반환한다. DB는 read-only 계정으로만 접근한다(ADR-007).

**MCP 도구 목록**

| 도구 | 입력 → 출력 | 목적 |
| --- | --- | --- |
| `list_version_changes` | 기간 → 변경 이력 목록 | 후보 변경 수집 |
| `get_quality_timeseries` | 지표·기간·버전 그룹 → 시계열 | 저하 시작 시점 확인 |
| `compare_versions` | 버전 A·B → 지표 차이·표본 수 | 변경 전후 품질 비교 |
| `search_traces` | 조건(버전·점수 범위) → 트레이스 요약 | 저하 사례 직접 확인 |
| `get_judge_feedback` | trace_id → 채점 근거 | 저하 유형(환각/누락/형식) 파악 |

**안전 장치**

- 호출 횟수 상한(`MAX_STEPS=12`) + 토큰 상한(`TOKEN_BUDGET=60,000`)
- 상한 도달 시 규칙 기반 결과(직전 변경 지목)로 대체 → `agent_fallback=true`

**입력 데이터:** `incidents` 레코드, 해당 기간의 변경 이력·트레이스·채점 결과.

**출력 데이터:** `incidents.agent_result` (원인 후보 순위·신뢰도·근거), `agent_steps` (도구 호출 기록), Slack 보고.

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| 호출·토큰 상한 도달 | 규칙 기반 결과로 대체, `agent_fallback=true` |
| 결론 JSON 구조 검증 실패 | 1회 재시도 후 폴백 |
| 에이전트 30분 미응답 | 스케줄러가 폴백 처리 후 RESOLVED |

**관련 ADR:** ADR-007 (직접 루프 + MCP 조회 전용)

**인수 기준**

- 주입 변경을 정답으로 Top-1·Top-3 정확도를 자동 계산하고, 규칙 기반 기준선과 비교할 수 있다.
- 모든 도구 호출이 `agent_steps`에 순서대로 남아 인시던트 상세 화면에 표시된다.
- `agent_fallback=true`인 인시던트는 에이전트 성능 집계에서 제외된다.

### 1.7 품질 저하 주입 프레임워크

**문제:** 품질 저하가 "실제로 일어난" 데이터가 없으면 탐지 성능도 원인 지목 정확도도 측정할 수 없다.

**동작 방식**

YAML 시나리오 파일에 기준 설정, 주입 시점, 변경 내용, 트래픽(질문 집합·rps·지속 시간), 랜덤 시드를 적고 실행한다. 트래픽 생성기가 고정 질문 집합을 재생하고, 정해진 시점에 설정이 런타임으로 교체된다(`source=injection`으로 `version_changes`에 기록).

```yaml
# scenarios/SCN-001-prompt-change.yaml
scenario_id: SCN-001
baseline:
  prompt: v1.2
  model: claude-haiku-current
  top_k: 5
  chunk_size: 512
inject:
  at_minute: 30
  change:
    prompt: v1.3-terse      # 이 변경이 정답 라벨
traffic:
  question_set: msmarco_eval_v1
  rps: 0.5
  duration_min: 90
seed: 42                    # 재현성 확보
```

**주입 시나리오 5종**

| 시나리오 | 주입 내용 | 대응 실제 사고 유형 |
| --- | --- | --- |
| SCN-001 | 시스템 프롬프트 변경 | Anthropic 2026.04 시스템 프롬프트 변경 |
| SCN-002 | 모델 교체(소형 이전 세대) | 모델 기본 설정 변경 |
| SCN-003 | top-k 축소 | 추론 강도 기본값 하향 |
| SCN-004 | 청크 크기 변경 | 인프라·캐시 설정 변경 |
| SCN-005 | 검색 인덱스 손상(근거 문서 일부 누락) | 문서 동기화 실패·캐시 결함 |
- **디코이 변경:** 각 시나리오에 무관한 변경을 섞어 "직전 변경을 고르면 항상 맞는" 상황을 막는다.
- **정답 라벨:** `is_decoy=false`인 `injection_events.version_change_id`가 곧 정답이다.

**입력 데이터:** 시나리오 YAML, `msmarco_eval_v1` 질문 집합(data.md 참조).

**출력 데이터:** `injection_runs`, `injection_events`(= 정답 라벨), 실험 구간의 트레이스·점수.

**예외 상황**

| 상황 | 동작 |
| --- | --- |
| 주입 실패 | 회차를 `ABORTED`로 표시. **해당 회차 데이터는 지표에서 제외** |
| 부분 주입 데이터 | 정답 라벨을 오염시키므로 전체 폐기 후 재실행 |

**관련 ADR:** ADR-026 (YAML + 런타임 교체)

**인수 기준**

- 같은 시드로 재실행했을 때 같은 질문 순서·주입 시점이 재현된다.
- SP2에서 수동 주입 1개로 품질 그래프 하락을 시연할 수 있다.
- SP3에서 시나리오 5종 × 10회 실험의 탐지율·탐지 지연·오탐 횟수를 보고할 수 있다.

## 4. 설계 방어 포인트

예상되는 평가 질문과 대응 논리를 미리 정리한다.

**Q1. Langfuse·Phoenix로 이미 되는 것 아닌가?**

요청 기록·평가·비용 추적은 그 도구들도 제공한다. 우리가 다른 것은 세 가지다.
① 경량 모델 전수 검사 + LLM 선별 검사의 **비용 구조를 실험으로 제시**한다.
② 품질 저하와 변경 이력을 연결해 **원인 후보를 자동으로 지목**한다.
③ 주입한 변경을 정답으로 삼아 그 지목 정확도를 **정량 평가**한다.
기능의 유무가 아니라 측정 결과가 산출물이다.

**Q2. 직접 학습한 모델이 공개 모델보다 못하면 실패 아닌가?**

개선 축을 정확도가 아니라 **추론 효율(크기·지연)**로 잡았다. 1단계는 CPU 전수 검사가 목적이므로 같은 정확도에서 더 싸게 도는 모델이 곧 기여다. 정확도–효율 곡선으로 결과를 제시하며, 2단 구조의 비용 분석은 1단계 모델의 출처와 무관하게 성립한다(ADR-028).

**Q3. LLM 채점자의 판정을 믿을 수 있나?**

믿을 수 있는지를 **먼저 측정한 뒤** 쓴다. MT-Bench 사람 평가와 일치율·Cohen's kappa를 비교하고, 순서 교환 재채점으로 위치 편향을, 길이–승패 관계로 길이 편향을 확인한다. 생성(소형)과 채점(중형)의 모델 등급을 분리하고, 표본 100~200건을 다른 제공자 채점자로 교차 검증한다(ADR-015).

**Q4. 품질 저하를 직접 주입하는 건 인위적이지 않나?**

시나리오 5종은 공개된 실제 사고 유형(시스템 프롬프트 변경, 기본 설정 변경, 캐시·인프라 결함, 문서 동기화 실패)에 대응시켜 설계했다. 주입 없이는 정답 라벨이 없어 탐지 성능을 측정할 수 없다. 또한 디코이 변경을 섞어 "직전 변경을 고르면 맞는" 쉬운 문제가 되지 않게 했다(ADR-026).

**Q5. 에이전트가 원인을 틀리게 지목하면?**

그래서 **조치 권한을 주지 않았다.** DB read-only 조회만 하고 결론과 근거를 제시하며, 롤백은 사람이 결정한다. 조사 과정을 화면에 공개해 결론을 검증할 수 있게 했고, 규칙 기반 기준선과 정확도를 비교해 "틀리는 정도"까지 수치로 보고한다(ADR-007).

**Q6. 단일 서버인데 실제 운영에서 쓸 수 있나?**

8주 일정에서 증명하려는 것은 처리 규모가 아니라 **구조의 타당성**이다. 수집은 비동기 배치, 검사는 요청 경로와 분리된 워커, 작업 큐는 트랜잭션 보장 구조로 설계했으므로 워커 수와 큐만 교체하면 수평 확장 경로가 열려 있다. k3s 이전은 SP3 선택 항목으로 남겨 뒀다(ADR-014).
