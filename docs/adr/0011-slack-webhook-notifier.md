# ADR-011: 알림 채널은 Slack Incoming Webhook으로 시작하고 Notifier 인터페이스로 추상화한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-18 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

드리프트가 감지되면 하락 시점과 원인 추정을 담아 알림을 보내야 한다. 데모에서는 "변경 → 그래프 하락 → 알림 도착"이 한 흐름으로 보여야 하므로 전달 속도와 가시성이 중요하다. 예산은 추가 지출 없이 해결해야 한다.

## 결정 근거

- 추가 비용 없이 사용 가능한지.
- 데모에서의 가시성과 전달 지연.
- 메시지 구조화(원인 후보·근거·링크) 가능성.
- 다른 채널로 교체할 수 있는 여지.

## 고려한 옵션들

- 옵션 1: 이메일 (SMTP)
- 옵션 2: Slack Incoming Webhook
- 옵션 3: Slack Bot Token + Block Kit

## 결정

옵션 2 **Slack Incoming Webhook**으로 시작하고, 발송 지점을 `Notifier` 인터페이스 뒤로 숨긴다. 무료 플랜으로 충분하고 실무 관제의 표준 채널이며, 발표 중 알림이 즉시 보이기 때문이다. 메시지 서식이 더 필요해지면 같은 인터페이스 아래에서 Bot Token + Block Kit 구현체로 교체한다.

## 결과

**긍정적**

- 비용 0으로 즉시 동작하고 데모 가시성이 좋다.
- 인터페이스 추상화 덕분에 이메일·웹훅 등 다른 채널 추가가 쉽다.

**부정적**

- Webhook은 메시지 수정·스레드 관리 등 고급 기능이 제한된다.
- Webhook URL이 유출되면 누구나 발송할 수 있어 비밀값 관리가 필요하다(ADR-021).

**후속 작업**

- `Notifier` 인터페이스와 Slack 구현체 작성 (T1-18)
- 인시던트당 1회 알림·쿨다운 로직 구현 및 테스트 (8.2-8)
- Webhook URL을 SSM Parameter Store에 보관

## 옵션별 장단점

### 옵션 1 — 이메일

- 장점: 외부 서비스 의존이 적다.
- 단점: 전달 지연과 스팸 분류 위험이 있어 데모에 부적합하다.

### 옵션 2 — Slack Webhook (채택)

- 장점: 설정이 가장 단순하고 비용이 없다.
- 단점: 메시지 편집·상호작용 기능이 없다.

### 옵션 3 — Slack Bot Token + Block Kit

- 장점: 구조화된 메시지와 상호작용 버튼을 쓸 수 있다.
- 단점: 앱 설치·권한 설정 비용이 들어 초기 단계에는 과하다.
