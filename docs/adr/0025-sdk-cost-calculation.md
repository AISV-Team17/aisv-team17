# ADR-025: 요청 단위 비용은 제공자 청구 API 대신 SDK 내부 단가표로 계산한다

| 항목 | 값 |
| --- | --- |
| **상태** | 제안됨 — 실제 청구액 오차 검증 후 수락됨으로 갱신 |
| **날짜** | 2026-10-25 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

이 프로젝트의 핵심 지표는 "2단 구조가 LLM 단독 전수 채점 대비 비용을 얼마나 줄이는가"다. 비용은 요청 단위·버전 단위로 즉시 집계되어야 대시보드와 라우팅 정책 화면이 성립한다. 제공자의 사용량·청구 데이터는 집계 지연이 있고 요청 단위로 분해되지 않으며, 계정 전체 사용량에 실험 외 호출이 섞인다.

## 결정 근거

- 요청·버전 단위 분해 가능 여부.
- 집계 지연(실시간 대시보드 요건).
- 실제 청구액과의 오차.
- 제공자 종속성.

## 고려한 옵션들

- 옵션 1: 제공자 사용량/청구 API를 주기적으로 조회해 배분
- 옵션 2: SDK가 토큰 수 × 내부 단가표로 요청 단위 비용을 계산해 속성으로 기록
- 옵션 3: 둘 다 기록하고 정기적으로 대조

## 결정

옵션 2 **SDK 내부 단가표 계산**을 기본으로 하고, 실제 청구액과의 **오차를 1회 이상 검증**(8.2-5)하는 방식을 택한다. 요청마다 버전·라우팅 사유와 함께 비용이 붙어야 "τ·r을 바꾸면 비용이 이렇게 변한다"는 화면과 실험이 가능한데, 청구 API로는 이 분해가 불가능하다. 검증 결과에 따라 옵션 3으로 보강할지 SP3에서 재판단한다.

## 결과

**긍정적**

- 요청·버전·라우팅 사유별 비용 집계가 즉시 가능해 핵심 지표 산출 경로가 열린다.
- 제공자 API 호출 없이 계산되어 집계 지연이 없다.

**부정적**

- 단가표가 낡으면 계산값이 실제 청구와 벌어진다.
- Batch API 할인 등 특수 요금을 반영하려면 단가표 로직이 복잡해진다.

**후속 작업**

- 단가표를 설정 파일로 분리하고 적용 시점을 버전으로 기록
- Batch API 할인(50%)과 캐시 적중 반영 규칙 정의
- 실제 사용량 대비 오차율 측정·보고 (8.2-5)

## 옵션별 장단점

### 옵션 1 — 제공자 청구 API

- 장점: 실제 청구액과 정확히 일치한다.
- 단점: 요청 단위 분해가 불가능하고 집계가 지연되어 대시보드·정책 실험에 쓸 수 없다.

### 옵션 2 — 내부 단가표 (채택)

- 장점: 요청 단위 즉시 계산, 버전·라우팅 사유별 분해 가능.
- 단점: 단가 갱신과 할인 반영이 수동이다.

### 옵션 3 — 병행 기록 후 대조

- 장점: 정확성과 분해 가능성을 모두 얻는다.
- 단점: 구현·운영 부담이 두 배가 된다. 검증 필요 시점에만 수동으로 수행하는 편이 낫다.
