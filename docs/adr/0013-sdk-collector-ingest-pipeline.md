# ADR-013: 수집 경로를 SDK → OTel Collector → Ingest API로 구성한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-20 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

## 컨텍스트

SDK가 내보내는 텔레메트리는 트레이스(검사 대상)와 메트릭(Prometheus 적재)으로 성격이 다르다. 두 종류를 Ingest API 한 곳에서 받으면 표준 OTLP(OpenTelemetry Protocol) 수신기와 프로토콜 처리를 직접 구현해야 하고, 백엔드를 바꿀 때마다 앱 코드가 영향을 받는다. 한편 단일 서버 메모리는 제한되어 있어 컨테이너를 늘리는 결정은 비용이 따른다.

## 결정 근거

- Ingest API 구현 범위의 축소.
- 메트릭·트레이스 분배 유연성.
- 도구 독립성(다른 관측 백엔드 동시 전송 가능 여부).
- 메모리 비용.

## 고려한 옵션들

- 옵션 1: SDK → Ingest API 직접 전송
- 옵션 2: SDK → OTel Collector → Ingest API (메트릭은 Collector가 Prometheus로 분배)
- 옵션 3: SDK → Collector → 외부 관측 백엔드 (자체 저장 없음)

## 결정

옵션 2 **Collector 경유**를 선택한다. 표준 OTLP 수신을 Collector가 맡으면 Ingest API는 검증·저장·작업 등록이라는 본래 책임에만 집중할 수 있고, 같은 데이터를 다른 관측 도구로 동시에 보내 "특정 도구에 묶이지 않는다"는 주장을 실제로 시연할 수 있다. 옵션 3은 자체 검사 파이프라인이 사라지므로 프로젝트 목적과 맞지 않는다. 늘어나는 메모리는 Collector에 256MB 한도를 걸어 통제한다.

## 결정

**긍정적**

- Ingest API가 OTLP 수신기를 직접 구현할 필요가 없다.
- 메트릭은 Prometheus, 트레이스는 Ingest API로 자동 분배된다.
- 수집 백엔드를 교체·추가해도 앱 코드를 수정하지 않는다.

**부정적**

- 컨테이너가 하나 늘고 메모리를 추가로 쓴다.
- 경로가 한 단계 길어져 장애 지점이 하나 추가된다(비동기라 서비스에는 영향 없음).

**후속 작업**

- Collector 이미지 버전 고정과 `mem_limit` 256MB 설정
- `otlphttp` exporter → Ingest API, Prometheus exporter 파이프라인 구성 (T1-07)
- Collector 강제 종료 시 서비스 정상 동작 확인 (8.2-2)

## 옵션별 장단점

### 옵션 1 — 직접 전송

- 장점: 경로가 가장 짧고 컨테이너가 늘지 않는다.
- 단점: OTLP 수신·프로토콜 처리를 직접 구현해야 하고, 메트릭 분배를 따로 만들어야 한다.

### 옵션 2 — Collector 경유 (채택)

- 장점: 구현 단순화, 분배 유연성, 도구 독립성 시연 가능.
- 단점: 컨테이너·메모리 추가.

### 옵션 3 — 외부 백엔드로 전송

- 장점: 저장·조회 구현이 전혀 필요 없다.
- 단점: 2단 검사·원인 분석이라는 프로젝트의 본체가 사라진다.
