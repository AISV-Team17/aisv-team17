# ADR-018: 프론트엔드를 Netlify가 아닌 동일 EC2에 함께 배포해 같은 출처를 유지한다

## 컨텍스트

팀 템플릿의 기본 배포 방식은 "백엔드는 EC2, 프론트엔드는 Netlify"다. 그러나 콘솔 인증이 httpOnly 세션 쿠키(ADR-017)이므로, 프론트와 API의 출처가 다르면 SameSite=None·Secure 설정과 CORS credentials 허용이 필요해지고 브라우저 정책 변화에 취약해진다. 또한 Grafana 패널 임베드도 동일 출처 뒤에 두는 편이 단순하다.

## 결정 근거

- 세션 쿠키 전송의 단순성(크로스 사이트 설정 회피).
- 배포 경로의 수(운영 부담).
- CDN·빌드 편의.
- 비용.

## 고려한 옵션들

- 옵션 1: Netlify에 프론트 배포 + EC2 API (교차 출처)
- 옵션 2: EC2 단일 서버에 Next.js 컨테이너를 함께 배포(동일 출처, 리버스 프록시로 `/api` 분기)
- 옵션 3: 정적 빌드 산출물을 API 서버가 직접 서빙

## 결정

옵션 2 **동일 EC2 + 리버스 프록시**를 선택한다. 쿠키가 같은 출처 안에서만 오가면 SameSite·CORS 설정이 사실상 불필요해지고, 배포 경로가 GitHub Actions → GHCR → EC2 하나로 통일되어 2인 팀의 운영 부담이 줄어든다. 옵션 3은 Next.js의 App Router 기능(서버 컴포넌트 등)을 포기해야 해 제외했다.

## 결과

**긍정적**

- 세션 쿠키가 별도 설정 없이 동작하고 CORS 예외를 둘 필요가 없다.
- 배포 파이프라인과 롤백 절차가 하나로 유지된다.
- Grafana 임베드도 같은 도메인 뒤에서 통제된다.

**부정적**

- CDN 캐싱 이점이 없고 정적 자원까지 EC2가 서빙한다(트래픽 규모상 문제 없음).
- 프론트 빌드가 서버 가동 상태에 묶인다.

**후속 작업**

- 리버스 프록시(Caddy 또는 Nginx) 설정과 `/api` 경로 분기
- Next.js 컨테이너 `mem_limit` 배정
- 기획서 0장 배포 방식 표기 갱신 — 완료

## 옵션별 장단점

### 옵션 1 — Netlify 분리 배포

- 장점: CDN·프리뷰 배포 등 프론트 개발 편의가 크다.
- 단점: 교차 출처가 되어 쿠키·CORS 설정 부담과 실패 지점이 늘어난다.
- 단점: 배포 경로가 둘로 나뉜다.

### 옵션 2 — 동일 EC2 배포 (채택)

- 장점: 인증·배포·임베드가 모두 단순해진다.
- 단점: CDN 이점을 포기하고 서버 자원을 더 쓴다.

### 옵션 3 — API 서버가 정적 파일 서빙

- 장점: 컨테이너가 하나 줄어든다.
- 단점: Next.js 서버 기능을 쓸 수 없어 화면 구현 선택지가 좁아진다.
