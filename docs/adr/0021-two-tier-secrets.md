# ADR-021: 비밀값은 로컬 .env / GitHub Secrets 2계층으로 분리하고 서버에는 SCP로 주입한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-31 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

## 컨텍스트

관리해야 할 비밀값은 Claude API Key, Slack Webhook URL, DB 비밀번호, 세션 서명 키, GHCR pull 토큰 등이다. 이들이 저장소에 들어가면 공개 저장소 여부와 무관하게 회수가 어렵고, 특히 LLM API Key 유출은 즉시 과금 사고로 이어진다. 실행 환경은 로컬·CI·서버 셋이다.

## 결정 근거

- 저장소 유출 위험 차단.
- 환경별 접근 경로의 명확성.
- 값 교체 시 반영 범위.
- 추가 비용.

## 고려한 옵션들

- 옵션 1: 모든 환경에서 `.env` 파일 사용(서버에도 직접 복사)
- 옵션 2: AWS Secrets Manager 전면 도입
- 옵션 3: 로컬 `.env`(gitignore) / CI는 GitHub Secrets / 서버는 `.env`(CD 시 SCP 또는 Actions로 주입)

## 결정

옵션 3 **2계층 분리**를 선택한다. AWS 이탈로 SSM Parameter Store를 사용할 수 없다. 서버 비밀값은 CD 파이프라인에서 GitHub Secrets에 저장된 값을 SCP로 `.env` 파일에 써넣는 방식으로 주입한다. 계층이 줄어 동기화 불일치 위험도 감소한다.

## 결과

**긍정적**

- 저장소에 비밀값이 존재하지 않는다.
- 계층이 2개로 줄어 관리 대상이 단순하다.
- AWS 없이 동작하므로 클라우드 종속성이 없다.

**부정적**

- 서버의 `.env`가 디스크에 평문으로 존재하므로 파일 권한(`chmod 600`)을 반드시 설정해야 한다.
- 로컬 `.env` 공유는 수동이라 팀원 간 전달 절차가 필요하다.

**후속 작업**

- `.env.example` 작성과 `.gitignore` 확인
- CD 워크플로에 SCP 스텝 추가 — GitHub Secrets 값을 서버 `.env`에 쓰기
- 서버 `.env` 파일 권한 `chmod 600` 런북에 명시
- 저장소 비밀값 스캔(gitleaks 등) CI 단계 추가 검토

## 옵션별 장단점

### 옵션 1 — `.env` 전면 사용

- 장점: 구성이 가장 단순하다.
- 단점: 서버 파일 복사 과정에서 유출 위험이 크고 접근 통제가 없다.

### 옵션 2 — Secrets Manager

- 장점: 자동 교체·버저닝 등 기능이 풍부하다.
- 단점: 비밀 개수당 비용이 발생해 학생 팀 예산에 불필요하다.

### 옵션 3 — 3계층 분리 (채택)

- 장점: 환경별 권한이 명확하고 비용이 거의 없다.
- 단점: 값 동기화 관리가 필요하다.
