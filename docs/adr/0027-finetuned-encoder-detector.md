# ADR-027: 자체 미세조정 인코더를 1단계 탐지 모델로 채택하고 LettuceDetect를 기준선 겸 임시 모델로 사용한다

| 항목 | 값 |
| --- | --- |
| **상태** | 제안됨 — SP2 1차 학습 결과 후 갱신 |
| **날짜** | 2026-10-24 |
| **작성자** | `AI-MDL` |
| **검토자** | `AI-SVC` |

---

## 컨텍스트

2단 품질 검사(Cascade)의 1단계는 EC2 t3.large(2 vCPU, 8GiB) CPU에서 모든 응답을 검사해야 한다. GPU를 쓰면 "저비용 전수 감시" 전제가 깨진다. 1단계 출력은 응답 점수(0~1)와 근거 없는 구간(토큰 단위)이며, 트레이스 상세 화면의 환각 구간 하이라이트에 그대로 쓰인다. 학습·평가 데이터는 RAGTruth(영어)이고, 서비스 언어도 영어다(ADR-016).

공개 모델 LettuceDetect는 ModernBERT를 RAGTruth로 학습한 토큰 분류 모델이다. RAGTruth 응답 단위 F1이 large 기준 79.22%로 보고되어, GPT-4 Turbo 프롬프트 방식(63.4%)과 기존 인코더 모델 Luna(65.4%)를 상회한다. 다만 8B LLM을 미세조정한 RAG-HAT(83.9%)이 더 높으므로 인코더 방식이 전체 최고는 아니다.

## 결정 근거

- CPU 서빙 가능 여부(GPU 없이 전수 검사 실현).
- 모델 파트의 연구 기여 확보(공개 모델만 쓰면 기여가 없다).
- SP2 일정(11/4)까지 파이프라인을 먼저 완성해야 하므로 임시 모델이 필요하다.
- 기준선을 못 넘더라도 정확도–효율 곡선으로 결과를 방어할 수 있어야 한다(ADR-028).

## 고려한 옵션들

- 옵션 1: LLM-as-a-Judge로 전수 검사
- 옵션 2: 8B LLM 미세조정 (RAG-HAT 계열)
- 옵션 3: LettuceDetect를 그대로 사용 (기준선으로만 활용)
- 옵션 4: 인코더(ModernBERT·DeBERTa-v3)를 크기별로 RAGTruth에 미세조정 + ONNX·INT8로 CPU 서빙

## 결정

**최종 1단계 모델:** 옵션 4 **자체 미세조정 인코더**를 선택한다.

- 백본 후보: ModernBERT(base·large), DeBERTa-v3(크기별)
- 학습 우선순위: ModernBERT-base(기준선과 같은 백본) → 더 작은 백본 → 나머지 크기
- 문제 형식: 문맥·질문·답변을 이어 붙인 입력에 대한 토큰 분류. 답변 토큰이 근거로 뒷받침되는지를 분류하며, 문맥·질문 토큰은 손실에서 제외한다.
- 서빙: Hugging Face Optimum으로 ONNX 변환 → 동적 INT8 양자화 → ONNX Runtime(CPU) (ADR-023)

**기준선 겸 임시 모델:** 옵션 3 **LettuceDetect**를 SP2 일정 안에 파이프라인을 완성하기 위한 임시 모델로 사용하고, 공정 비교를 위한 기준선으로도 유지한다. `Detector` 인터페이스(ADR-024) 뒤에 두어 설정 한 줄로 교체한다.

**교체 기준:** 자체 모델이 같은 평가 코드에서 "합의한 F1 손실 범위" 안이면서 CPU p95 지연 또는 모델 크기가 줄어들면 교체한다. 손실 허용 범위는 SP2 1차 실험 후 두 파트가 정확도–효율 곡선을 보고 합의한다.

## 결과

**긍정적**

- `Detector` 인터페이스 뒤에서 공개 모델과 자체 모델을 같은 평가 코드로 공정하게 비교할 수 있다.
- SP2 파이프라인을 LettuceDetect로 먼저 완성해 일정 의존이 끊긴다.
- 정확도–효율 곡선이 과제 A의 연구 결과물이자 ADR-028의 핵심 산출물이 된다.

**부정적**

- 학습에 GPU가 필요해 Colab·Kaggle·교내 GPU 조달이 필요하다.
- 자체 모델이 기준선을 못 넘을 수 있다(대응: ADR-028 개선 축 설정).

**후속 작업**

- `Detector` 구현체 2개 등록: LettuceDetect 래퍼, 자체 모델 ONNX 래퍼 (ADR-024와 연동)
- 허용 F1 손실 폭 기준을 `AI-SVC`와 합의 (ADR-023 미결 사항과 연동, 11/11까지)
- **stage 1 score 방향 확인**: 학습 시 RAGTruth의 환각 라벨(hallucinated) → 높은 score, 정상 라벨(supported) → 낮은 score가 되도록 출력을 설계한다. `score >= τ` 라우팅 규칙과 일치해야 한다(erd.md 1장 점수 방향 원칙).
- RAGTruth는 이전 세대 모델의 응답이므로, 자체 RAG 서비스의 주입 실험 데이터로 추가 평가해 한계를 확인한다.

## 옵션별 장단점

### 옵션 1 — LLM-as-a-Judge 전수 검사

- 장점: 구현이 단순하고 판정 이유를 자연어로 생성한다.
- 단점: 응답 1건당 생성 비용에 준하는 평가 비용 → 전수 감시가 경제적으로 불가능하다.

### 옵션 2 — 8B LLM 미세조정

- 장점: 현재 공개된 인코더 방식 중 가장 높은 정확도(RAG-HAT 83.9%).
- 단점: GPU 없이 CPU 서빙이 사실상 불가능해 "저비용 전수 감시" 전제가 깨진다.

### 옵션 3 — LettuceDetect 그대로 사용

- 장점: 즉시 사용 가능하고 검증된 성능이다.
- 단점: 모델 파트의 연구 기여가 없고, 크기·지연 개선 여지를 검토하지 않게 된다.

### 옵션 4 — 자체 미세조정 인코더 (채택)

- 장점: CPU 서빙 가능, 정확도–효율 곡선이라는 연구 결과 확보.
- 단점: 학습에 GPU가 필요하고 기준선을 못 넘을 위험이 있다.
