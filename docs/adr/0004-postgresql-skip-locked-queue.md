# ADR-004: 작업 큐는 별도 브로커 대신 PostgreSQL의 SKIP LOCKED로 구현한다

## 컨텍스트

수집된 트레이스는 비동기 워커가 꺼내 1·2단계 검사를 수행하므로 작업 큐가 필요하다. 이때 가장 위험한 상태는 "트레이스는 저장되었는데 검사 작업은 등록되지 않은" 유실이다. 이 상태가 생기면 전수 검사라는 전제 자체가 깨진다. 한편 서버는 EC2 t3.large 한 대이고 PostgreSQL·Collector·워커·콘솔·Grafana 등이 메모리 8GiB를 나눠 쓴다.

## 결정 근거

- 저장과 작업 등록의 원자성(유실 방지).
- 단일 서버에서의 컨테이너 수·메모리 비용.
- 현재 트래픽 규모(실험 기준 0.5 rps)에서의 충분성.
- 운영 복잡도.

## 고려한 옵션들

- 옵션 1: Redis + RQ/Celery
- 옵션 2: RabbitMQ
- 옵션 3: PostgreSQL 테이블 + `SELECT … FOR UPDATE SKIP LOCKED`

## 결정

옵션 3 **PostgreSQL 작업 큐(`SKIP LOCKED`)**를 선택한다. 트레이스 저장과 `eval_jobs` 등록을 **하나의 트랜잭션**으로 묶을 수 있어 유실 가능성이 구조적으로 사라지고, 별도 브로커 컨테이너를 띄우지 않아 단일 서버의 메모리 예산을 아낄 수 있다. 외부 브로커를 쓰면 DB 커밋과 큐 발행 사이에 이중 쓰기 문제가 생겨 아웃박스 패턴 같은 추가 장치가 필요해지는데, 현재 처리량에서는 그 복잡도를 치를 이유가 없다.

## 결과

**긍정적**

- "저장은 됐는데 검사는 안 된" 상태가 원천적으로 발생하지 않는다(T1-07 인수 기준).
- 컨테이너가 하나 줄어 메모리와 운영 부담이 함께 줄어든다.
- 작업 상태·재시도 횟수·점유 시각을 SQL로 직접 조회할 수 있어 디버깅이 쉽다.

**부정적**

- 워커가 폴링하므로 처리량이 커지면 DB 부하가 늘어난다.
- 지연 작업 예약, 우선순위 큐 같은 기능은 직접 구현해야 한다.

**후속 작업**

- `eval_jobs` 스키마(`status`, `attempts`, `locked_at`)와 인덱스 설계 (T1-07)
- 워커 재기동 시 점유 해제(stale lock) 처리와 재시도 상한 정의
- 폴링 주기 기본값 결정 및 부하 측정 후 조정

## 옵션별 장단점

### 옵션 1 — Redis + Celery/RQ

- 장점: 처리량이 높고 생태계가 성숙해 재시도·스케줄링 기능을 바로 쓸 수 있다.
- 단점: DB 커밋과 큐 발행이 분리되어 이중 쓰기 문제를 따로 막아야 한다.
- 단점: 컨테이너와 메모리가 추가로 필요하고, Redis는 기본 설정에서 영속성이 약하다.

### 옵션 2 — RabbitMQ

- 장점: 전달 보장과 라우팅 기능이 가장 풍부하다.
- 단점: 이 규모에 비해 운영 복잡도와 자원 요구가 과도하다.

### 옵션 3 — PostgreSQL SKIP LOCKED (채택)

- 장점: 저장과 등록의 원자성을 트랜잭션 하나로 보장한다.
- 장점: 추가 인프라가 없고 상태를 SQL로 들여다볼 수 있다.
- 단점: 폴링 비용이 있고 고급 큐 기능은 직접 만들어야 한다.
