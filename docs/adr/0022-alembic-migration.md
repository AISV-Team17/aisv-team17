# ADR-022: DB 스키마 변경은 Alembic 마이그레이션을 단일 경로로 삼는다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-25 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

스키마는 트레이스·버전 이력·검사 결과·임베딩·인시던트·사용자 등 여러 테이블로 구성되고, SP2~SP3 동안 계속 바뀐다. 두 파트가 같은 DB를 쓰고 ERD 문서도 유지해야 하므로, 변경 경로가 여러 개면 로컬·서버·문서가 어긋난다. 또한 실험 구간 중에 스키마가 바뀌면 이전 데이터와의 비교가 깨질 수 있다.

## 결정 근거

- 환경 간 스키마 일치.
- 변경 이력의 추적 가능성(리뷰 대상 여부).
- 롤백 가능성.
- ERD 문서와의 동기화.

## 고려한 옵션들

- 옵션 1: SQL 스크립트를 직접 실행
- 옵션 2: ORM의 자동 생성(`create_all`) 사용
- 옵션 3: Alembic 마이그레이션을 유일한 변경 경로로 사용

## 결정

옵션 3 **Alembic 마이그레이션 단일 경로**를 선택한다. 마이그레이션 파일이 코드로 남아 PR 리뷰 대상이 되고(CODEOWNERS 승인 필수 경로), 로컬·CI·서버가 같은 리비전으로 수렴하며, 문제 시 다운그레이드 경로가 존재한다. `create_all`은 변경 이력이 남지 않고 기존 테이블 변경을 처리하지 못해 운영 중 사용할 수 없다.

## 결과

**긍정적**

- 스키마의 모든 변경이 커밋과 리뷰를 거친다.
- 환경 간 스키마 불일치로 인한 통합 실패가 줄어든다.
- ERD는 마이그레이션을 원본으로 삼아 동기화 시점을 정의할 수 있다.

**부정적**

- 작은 변경에도 리비전 파일을 만들어야 한다.
- 두 파트가 동시에 리비전을 만들면 head가 갈라져 병합 작업이 필요하다.

**후속 작업**

- 초기 리비전 작성과 배포 시 자동 `upgrade head` 단계 구성
- 리비전 충돌 발생 시 처리 절차를 런북에 기록
- ERDCloud 동기화 시점을 스프린트 종료로 고정

---

## 옵션별 장단점

### 옵션 1 — 직접 SQL 실행

- 장점: 즉시 적용되고 도구가 필요 없다.
- 단점: 적용 여부가 환경마다 달라지고 이력이 남지 않는다.

### 옵션 2 — ORM 자동 생성

- 장점: 개발 초기에 가장 빠르다.
- 단점: 기존 테이블 변경·데이터 보존을 처리하지 못한다.

### 옵션 3 — Alembic (채택)

- 장점: 이력·리뷰·롤백을 모두 확보한다.
- 단점: 리비전 관리 부담과 head 충돌 가능성이 있다.
