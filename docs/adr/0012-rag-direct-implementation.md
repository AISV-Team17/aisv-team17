# ADR-012: 감시 대상 RAG 서비스는 프레임워크 없이 직접 구현한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-20 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

이 프로젝트의 RAG 서비스는 제품이 아니라 **실험 대상**이다. 주입 실험에서 top-k·청크 크기·프롬프트를 런타임에 바꿔야 하고, 검색·프롬프트 조립·생성 각 단계에 계측 스팬을 정확한 위치에 심어야 한다. LangChain·LlamaIndex는 이 세 단계를 추상화해 주지만, 내부에서 프롬프트를 조립하고 호출 경로를 감싸므로 설정 외부화와 계측 지점 통제가 간접적이 된다.

## 결정 근거

- 실험 변수(top-k·청크 크기·프롬프트)의 완전한 외부화 가능 여부.
- 계측 스팬 위치의 통제 가능 여부.
- 동작 원리를 설명할 수 있는지.
- 구현 비용.

## 고려한 옵션들

- 옵션 1: LangChain
- 옵션 2: LlamaIndex
- 옵션 3: 직접 구현(검색 → 프롬프트 조립 → LLM 호출), 로더·청크 분할만 라이브러리 유틸 사용

## 결정

옵션 3 **직접 구현**을 선택한다. 주입 실험의 정답 라벨이 "우리가 바꾼 설정"이므로 설정이 코드가 아니라 `configs/` 파일에 100% 외부화되어야 하고, 1단계 탐지의 입력이 되는 검색 문맥을 스팬에 정확히 남겨야 한다. 문서 로딩과 청크 분할은 실험 변수가 아니므로 라이브러리 유틸을 사용해 구현 비용을 줄인다.

## 결과

**긍정적**

- `configs/` 값만 바꾸면 런타임에 검색 설정이 바뀌어 주입 프레임워크가 단순해진다(ADR-026).
- 각 단계 스팬을 원하는 위치·속성으로 남길 수 있다.
- 프레임워크 내부 동작에 기대지 않아 발표에서 설계를 끝까지 설명할 수 있다.

**부정적**

- 리트리버·프롬프트 템플릿·재시도 로직을 직접 작성해야 한다.
- 고급 RAG 기법(재순위, 쿼리 재작성 등)을 쓰려면 매번 직접 구현해야 한다.

**후속 작업**

- `src/rag/` 모듈 구조(retriever / prompt / generator) 작성 (T1-15 선행)
- LLM 호출을 제공자 독립 인터페이스로 감싸기 (ADR-015와 연계)
- 청크 분할 유틸 선택과 고정 버전 기록

## 옵션별 장단점

#### 옵션 1 — LangChain

- 장점: 리트리버·체인·콜백이 갖춰져 초기 구현이 빠르다.
- 단점: 프롬프트 조립이 내부에 숨어 설정 외부화가 간접적이 된다.
- 단점: 버전 변화가 잦아 실험 재현성에 변수로 작용한다.

#### 옵션 2 — LlamaIndex

- 장점: 인덱싱·검색 추상화가 강하다.
- 단점: 인덱스 추상화가 두꺼워 "검색 인덱스 손상" 주입 시나리오를 다루기 번거롭다.

#### 옵션 3 — 직접 구현 (채택)

- 장점: 설정 외부화·계측 통제·설명 가능성을 모두 확보한다.
- 단점: 초기 구현량이 늘고 고급 기법은 직접 만들어야 한다.
