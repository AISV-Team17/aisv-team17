# ADR-009: 저장소는 모노레포로 운영하고 CODEOWNERS로 핵심 경로만 상호 리뷰를 강제한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-18 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

두 파트는 `Detector`·`DriftDetector` 같은 인터페이스를 공유하고, 모델 파트의 구현체가 서비스 파트의 워커에 플러그인된다. 인터페이스가 바뀌면 양쪽 코드가 함께 바뀌어야 한다. 동시에 2인 팀에서 모든 PR에 상호 승인을 요구하면 리뷰가 병목이 되어 병렬 개발이 막힌다.

## 결정 근거

- 인터페이스 변경을 한 번에 반영할 수 있는지.
- 리뷰 병목 최소화.
- CI 구성과 의존성 관리의 단순성.

## 고려한 옵션들

- 옵션 1: 파트별 멀티레포(서비스/모델 분리)
- 옵션 2: 모노레포 + 전 PR 상호 승인 필수
- 옵션 3: 모노레포 + CODEOWNERS로 핵심 경로만 승인 필수

## 결정

옵션 3 **모노레포 + 핵심 경로 CODEOWNERS**를 선택한다. 인터페이스 변경이 한 PR 안에서 양쪽에 반영되어야 계약 불일치로 인한 통합 실패를 막을 수 있고, 그러면서도 각자 영역의 일상적인 PR까지 상대 승인을 기다리면 2인 팀의 병렬 개발이 멈춘다. 승인 필수 경로는 인터페이스, 라우팅·지표 집계, 주입 시나리오, 모델·실험 설정, DB 마이그레이션, ADR로 한정한다.

## 결과

**긍정적**

- 인터페이스 변경과 그 영향이 한 커밋 범위에서 보인다.
- 핵심 경로는 양쪽이 내용을 알고 있어, 한 사람이 빠져도 진행이 가능하다(인력 공백 리스크 대응).
- CI·의존성·Docker 구성이 하나로 유지된다.

**부정적**

- 저장소가 커지고 CI 실행 시간이 늘어난다(경로 필터로 완화).
- 파트별 접근 권한을 세밀하게 나눌 수 없다.

**후속 작업**

- `CODEOWNERS` 작성과 브랜치 보호 규칙 설정
- 경로 기반 CI 트리거 필터 구성
- 브랜치 접두사 규칙(`svc/`, `mdl/`) 안내

## 옵션별 장단점

### 옵션 1 — 멀티레포

- 장점: 파트별 권한·CI가 깔끔하게 분리된다.
- 단점: 인터페이스 변경이 두 PR로 쪼개져 버전 불일치 구간이 생긴다.

### 옵션 2 — 모노레포 + 전면 승인

- 장점: 모든 변경을 양쪽이 알게 된다.
- 단점: 2인 팀에서 리뷰가 병목이 되어 병렬 개발 전제가 무너진다.

### 옵션 3 — 모노레포 + 선택적 승인 (채택)

- 장점: 계약 안정성과 개발 속도를 동시에 얻는다.
- 단점: 어떤 경로가 핵심인지 합의하고 유지해야 한다.
