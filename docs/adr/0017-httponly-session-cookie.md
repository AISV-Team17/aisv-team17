# ADR-017: 콘솔 인증은 JWT 대신 httpOnly 세션 쿠키로 구현한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-25 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

트레이스에는 사용자 질문과 LLM 응답 본문이 그대로 담긴다. 콘솔과 조회 API가 공개 IP에 노출되면 이 내용이 그대로 읽히므로 최소한의 접근 통제가 필요하다. 다만 회원가입·권한 등급·다중 테넌트는 범위 외(5.3)이고, 사용자는 시드로 만든 관리자 계정 하나뿐이다.

## 결정 근거

- 토큰 탈취 위험(XSS 노출 여부).
- 즉시 로그아웃·세션 무효화 가능 여부.
- 구현량(범위 외 기능에 쓰는 시간 최소화).
- 프론트엔드와의 통합 단순성.

## 고려한 옵션들

- 옵션 1: JWT를 localStorage에 보관
- 옵션 2: 서버 세션 + httpOnly·Secure 쿠키
- 옵션 3: Basic 인증 또는 리버스 프록시 수준 인증

## 결정

옵션 2 **서버 세션 + httpOnly·Secure 쿠키**를 선택한다. JavaScript에서 읽히지 않아 XSS로 인한 토큰 탈취 위험이 낮고, `sessions` 테이블의 행만 지우면 즉시 무효화할 수 있어 시연 중 사고 대응이 쉽다. 사용자가 사실상 한 명이므로 세션 저장 비용은 무시할 수 있다. Basic 인증은 로그아웃 처리와 UX가 나빠 콘솔에 부적합하다.

## 결과

**긍정적**

- 토큰이 JS에 노출되지 않아 공격 표면이 줄어든다.
- 세션 만료·강제 로그아웃을 DB 조작만으로 처리한다.
- 프론트엔드는 `credentials: 'include'`만 설정하면 되어 구현량이 적다.

**부정적**

- 프론트와 API가 다른 출처면 크로스 사이트 쿠키 설정이 필요하다 → ADR-018로 해소.
- CSRF(Cross-Site Request Forgery) 대비가 필요하다(SameSite=Lax 기본, 쓰기 요청 점검).

**후속 작업**

- `users` / `sessions` 스키마, argon2 해시, 시드 계정 생성 스크립트 (T1-12)
- SameSite·Secure 속성 설정과 만료 정책 결정
- 비로그인 Console API 호출 시 401 반환 테스트 (8.2-10)

## 옵션별 장단점

### 옵션 1 — JWT + localStorage

- 장점: 서버 상태가 없어 확장이 쉽다.
- 단점: XSS로 토큰이 유출될 수 있고, 발급된 토큰의 즉시 무효화가 어렵다.

### 옵션 2 — 세션 쿠키 (채택)

- 장점: XSS 내성과 즉시 무효화를 모두 갖춘다.
- 단점: 서버 상태가 필요하고 CSRF를 신경 써야 한다.

### 옵션 3 — Basic 인증 / 프록시 인증

- 장점: 구현이 가장 빠르다.
- 단점: 로그아웃·세션 관리가 불가능하고 UX가 나쁘다.
