# ADR-023: 1단계 탐지 모델 서빙은 PyTorch 직접 추론 대신 ONNX Runtime(CPU)으로 한다

| 항목 | 값 |
| --- | --- |
| **상태** | 제안됨 — SP2 실험 후 F1 손실 폭 확인 시 수락됨으로 갱신 |
| **날짜** | 2026-10-25 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

1단계 탐지는 모든 응답을 검사하므로 추론 비용이 곧 플랫폼 운영 비용이다. GPU를 쓰면 "저비용 전수 감시"라는 전제가 무너지므로 EC2 t3.large의 2 vCPU에서 돌아가야 한다. 동시에 `AI-MDL` 파트의 개선 축이 추론 효율(크기·지연)이라, 최적화 전후를 같은 코드 경로에서 비교할 수 있어야 한다.

## 결정 근거

- CPU 추론 지연과 처리량.
- 모델 크기(메모리 점유).
- 정확도 손실 폭.
- 학습 코드에서 서빙까지의 전환 비용.

## 고려한 옵션들

- 옵션 1: PyTorch 모델을 그대로 적재해 추론
- 옵션 2: ONNX 변환 + ONNX Runtime(CPU), 동적 INT8 양자화 적용
- 옵션 3: 외부 추론 서버(Triton 등) 분리 운영

## 결정

옵션 2 **ONNX Runtime(CPU) + 동적 INT8 양자화**를 선택한다. Hugging Face Optimum으로 export하면 학습 코드를 바꾸지 않고 그래프 최적화와 양자화를 적용할 수 있고, 같은 `Detector` 인터페이스 뒤에서 PyTorch 기준과 비교 측정하여 "정확도–효율 곡선"을 그대로 산출할 수 있다. 외부 추론 서버는 단일 서버 메모리 예산에서 감당하기 어렵다. **양자화로 인한 F1 손실 폭은 실험 결과이므로, SP3 측정 후 수락 여부를 확정한다.**

## 결과

**긍정적**

- GPU 없이 전수 검사가 가능해 비용 전제가 유지된다.
- 모델 크기·p95 지연 감소를 수치로 보고할 수 있어 ADR-028(과제 A 개선 축)의 기여와 직접 연결된다.
- 학습(PyTorch)과 서빙(ONNX)이 분리되어 모델 교체가 설정 변경으로 끝난다.

**부정적**

- 변환 단계가 파이프라인에 추가되고, 연산자 미지원 시 디버깅이 필요하다.
- 양자화로 정확도가 떨어질 수 있다(손실 폭 측정 후 임계 판단).

**후속 작업**

- 기준(PyTorch FP32) → ONNX → INT8 → 배치 처리 순으로 측정
- 허용 가능한 F1 손실 폭 기준을 `AI-MDL`과 합의 (ADR-027 미결 사항과 연동)
- 측정 후 이 ADR의 상태를 수락됨 또는 대체됨으로 갱신

## 옵션별 장단점

### 옵션 1 — PyTorch 직접 추론

- 장점: 변환 단계가 없어 학습 결과를 즉시 서빙할 수 있다.
- 단점: CPU 지연과 메모리 점유가 커 전수 검사 처리량을 맞추기 어렵다.

### 옵션 2 — ONNX Runtime + INT8 (채택, 측정 후 확정)

- 장점: CPU 지연·모델 크기를 줄이고 비교 실험 축을 제공한다.
- 단점: 변환 호환성 이슈와 정확도 손실 가능성이 있다.

### 옵션 3 — 외부 추론 서버

- 장점: 모델 버전 관리·배치 처리 기능이 성숙하다.
- 단점: 컨테이너·메모리 비용이 커 단일 서버 구성과 충돌한다.
