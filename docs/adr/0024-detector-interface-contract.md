# ADR-024: Detector·DriftDetector 인터페이스를 두 파트의 유일한 결합 지점으로 고정한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-25 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

---

## 컨텍스트

`AI-MDL`은 탐지 모델과 드리프트 판정 로직을 만들고, `AI-SVC`는 이를 워커·스케줄러에 연결한다. 모델 학습은 SP2 중반 이후에야 결과가 나오므로, 그때까지 서비스 파이프라인이 멈추면 일정이 무너진다. 반대로 서비스 쪽 구조가 늦게 정해지면 모델 쪽이 출력 형식을 확정하지 못한다.

## 결정 근거

- 두 파트가 서로를 기다리지 않고 병렬 개발할 수 있는지.
- 공개 모델 → 자체 모델 교체 비용.
- 실험 재현성(같은 평가 코드로 여러 구현 비교).
- 계약 변경 시 영향 범위.

## 고려한 옵션들

- 옵션 1: 모델 코드를 워커에 직접 임포트해 호출
- 옵션 2: 모델을 별도 HTTP 서비스로 분리해 호출
- 옵션 3: Python 인터페이스(`Detector`, `DriftDetector`)를 계약으로 두고 구현체를 설정으로 주입

## 결정

옵션 3 **인터페이스 계약 + 설정 주입**을 선택한다. `detect(context, question, answer) → (score, spans)` 같은 계약만 10/28까지 합의하면, 모델 학습이 끝나기 전에도 공개 모델(LettuceDetect) 구현체로 파이프라인 전체를 완성할 수 있고, 완성 후에는 설정 한 줄로 자체 모델로 바꿔 **같은 평가 코드로 공정하게 비교**할 수 있다. HTTP 분리는 단일 서버에서 불필요한 프로세스와 직렬화 비용을 더한다.

## 결과

**긍정적**

- 두 파트의 일정 의존이 끊겨 병렬 개발이 가능하다(T3-01).
- 공개 모델과 자체 모델을 동일 조건에서 비교할 수 있다.
- 드리프트 판정 3방식을 같은 인터페이스로 교체 실험할 수 있다.

**부정적**

- 계약을 바꾸려면 양쪽 코드와 테스트를 함께 수정해야 한다(모노레포로 완화).
- 인터페이스가 지나치게 좁으면 모델 쪽 표현력을 제약할 수 있다.

**후속 작업**

- `src/interfaces/`에 계약과 타입 정의, 더미 구현체 작성 (T3-01, 10/28까지)
- 계약 경로를 `CODEOWNERS` 승인 필수 경로에 포함
- 계약 준수 테스트(더미 + 실제 구현) 작성

## 옵션별 장단점

### 옵션 1 — 직접 임포트

- 장점: 가장 빠르고 코드가 적다.
- 단점: 모델 코드 구조가 바뀔 때마다 워커가 깨지고, 교체·비교가 어렵다.

### 옵션 2 — HTTP 서비스 분리

- 장점: 언어·배포 독립성이 생긴다.
- 단점: 단일 서버에서 프로세스와 직렬화 비용만 늘고 얻는 것이 적다.

### 옵션 3 — 인터페이스 계약 (채택)

- 장점: 병렬 개발, 교체 용이성, 공정 비교를 모두 확보한다.
- 단점: 계약 설계와 유지에 합의 비용이 든다.
