# ADR-005: 버전의 원본은 Git configs/ 파일로 두고 DB는 해시 레지스트리로 운영

| 항목 | 값 |

| **날짜** | 2026-10-16 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

## 컨텍스트

원인 변경 추적이 성립하려면 프롬프트·모델·검색 설정의 변경 이력이 빠짐없이 남아야 하고, 에이전트와 콘솔이 그 이력을 빠르게 조회할 수 있어야 한다. 동시에 품질 저하 주입 실험에서는 Git 커밋 없이 런타임에 설정을 바꾸므로, 커밋만을 이력의 원천으로 삼으면 실험 구간의 변경이 기록에서 누락된다.

## 결정 근거

- 변경 사유·주체가 남는지(감사 가능성).
- 에이전트·콘솔의 조회 성능과 단순성.
- 런타임 주입 변경까지 포함할 수 있는지.
- 원본이 둘로 갈라질 위험.

## 고려한 옵션들

- 옵션 1: Git 파일만 사용 (DB 미기록)
- 옵션 2: DB에서 버전을 생성·관리 (콘솔에서 편집)
- 옵션 3: Git 파일이 원본, 기동 시 내용 해시를 DB에 등록하는 레지스트리 병행

## 결정

옵션 3 **Git 원본 + DB 해시 레지스트리**를 선택한다. 변경 사유와 주체는 PR·커밋으로 남아야 하고(옵션 2는 이를 잃는다), 에이전트는 Git을 뒤지는 대신 SQL 한 번으로 기간별 변경 이력을 가져와야 하며(옵션 1은 이를 어렵게 한다), 주입 실험의 런타임 변경도 `source=injection`으로 같은 테이블에 들어와야 한다. 원본이 둘로 보일 위험은 "내용 해시가 같으면 같은 버전"이라는 단일 규칙으로 통제한다.

## 결과

**긍정적**

- 변경 이력에 배포(`deploy`)·주입(`injection`)·콘솔 설정 변경(`console`)이 한 테이블로 모여 원인 후보 수집이 단순해진다.
- 에이전트가 변경 내용(diff)까지 Git 커밋과 연결해 근거로 제시할 수 있다.
- 동일 내용 재배포는 해시가 같아 이력에 쌓이지 않는다(T1-06 인수 기준).

**부정적**

- 원본이 Git임을 팀이 계속 의식해야 한다. DB를 직접 수정하면 정합이 깨진다.
- 기동 시 해시 계산·등록 로직이 추가된다.

**후속 작업**

- `versions` / `version_changes` 스키마 확정과 해시 산출 규칙 문서화 (T1-05, T1-06)
- DB 직접 수정 금지를 CONTRIBUTING에 명시
- 콘솔 쓰기 기능이 `source=console`로 기록되는지 통합 테스트

## 옵션별 장단점

### 옵션 1 — Git 파일만 사용

- 장점: 원본이 하나뿐이라 정합 문제가 없다.
- 단점: 에이전트·콘솔이 Git을 파싱해야 해 조회가 느리고 복잡하다.
- 단점: 커밋 없는 런타임 주입 변경을 기록할 방법이 없다.

### 옵션 2 — DB 중심 관리

- 장점: 콘솔에서 바로 편집·조회할 수 있어 사용성이 좋다.
- 단점: 변경 사유가 코드 리뷰에 남지 않아 "왜 바꿨는가"를 잃는다.
- 단점: 설정이 코드와 분리되어 배포 재현성이 떨어진다.

### 옵션 3 — Git 원본 + DB 레지스트리 (채택)

- 장점: 감사 가능성과 조회 성능을 모두 얻고, 주입 변경까지 한 이력으로 통합한다.
- 단점: 등록 로직과 "DB를 직접 고치지 않는다"는 규율이 필요하다.
