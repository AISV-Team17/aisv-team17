# ADR-029: 드리프트 탐지는 3가지 방식을 교체 가능한 구현체로 두고 실험으로 비교한다

| 항목 | 값 |
| --- | --- |
| **상태** | 제안됨 — SP3 실험 결과 후 기본 방식 확정 시 갱신 |
| **날짜** | 2026-10-24 |
| **작성자** | `AI-MDL` |
| **검토자** | `AI-SVC` |

---

## 컨텍스트

품질 저하는 HTTP 200과 정상 지연 속에서 조용히 일어난다. 응답 내용 기반 지표의 분포 변화로 잡아야 하며, 감시 대상은 품질 점수 시계열(`evaluations`)과 응답 임베딩(`embeddings`, all-MiniLM-L6-v2 384차원) 두 가지다.

임베딩 모델에는 입력 제약이 있다. all-MiniLM-L6-v2는 256 word piece를 초과하면 입력을 잘라낸다. 긴 응답은 앞부분만 임베딩에 반영되므로, 응답 길이 분포를 확인하고 필요하면 문장 단위 임베딩 평균을 검토한다.

운영 조건: Drift Monitor(APScheduler)가 5분 시간 창마다 판정한다. 실험 트래픽 0.5 rps 기준 창당 약 150건. CPU, 메모리 제한 환경이다. 판정 로직은 `AI-MDL`이 `DriftDetector` 구현체로 제공하고, 스케줄링·인시던트 생성은 `AI-SVC`가 맡는다(ADR-024).

**창 집계 기준 시각 결정:** 창 배분은 `traces.started_at` 기준으로 수행한다. `evaluations.created_at`이나 `embeddings.created_at`을 기준으로 삼지 않는다. 비동기 처리 지연이 창 귀속에 영향을 주지 않게 하기 위함이다(erd.md 1장 창 집계 기준 원칙).

## 결정 근거

- 어떤 판정 방식이 이 트래픽·시간 창·드리프트 유형에서 탐지 지연–오탐률 균형이 좋은지 전제를 두지 않는다.
- 비교 실험 자체가 과제 C의 연구 결과물이다.
- `DriftDetector` 인터페이스로 스케줄러 연동과 판정 로직을 분리해 병렬 개발한다.
- 운영 중 방식을 교체할 수 있어야 SP3 실험 결과에 따라 기본값을 바꿀 수 있다.

## 고려한 옵션들

- 옵션 1: 고정 임계값 단독 운용
- 옵션 2: 통계 검정(KS 검정) 단독 운용
- 옵션 3: 3방식(고정 임계값·통계 검정·임베딩 거리)을 `DriftDetector` 구현체로 두고 실험으로 비교

## 결정

옵션 3 **3방식 교체 가능 구현체**를 선택한다. 기본 방식을 미리 고정하지 않고, 시나리오 5종 × 10회 실험을 통해 탐지 지연–오탐률 균형 수치로 결정한다. SP3 실험 후 기본 방식을 이 ADR에 기록하고 상태를 갱신한다.

구현체 3종의 판정 대상과 초기안:

| 구현체 | 대상 | 판정 규칙 (초기안) |
| --- | --- | --- |
| `ThresholdDetector` | 창별 평균 점수·환각 비율 | 기준 창 평균 대비 변화량이 임계값 초과 |
| `KSTestDetector` | 창별 점수 분포 | 기준 창 vs 현재 창 2표본 KS 검정, p < α |
| `EmbeddingDistanceDetector` | 응답 임베딩 | 현재 창 중심점과 기준 중심점의 코사인 거리 > 임계값 |

**기준(reference) 구간 정의:** 직전 버전 변경 이후 정상 구간의 창들로 구성한다. 버전이 바뀌어도 기준을 즉시 갈아끼우지 않는다. 변경 직후 저하를 잡는 것이 목적이기 때문이다. 기준 갱신 규칙은 `AI-SVC`가 `policies.md`에서 확정한다.

**임계값 보정:** 임계값을 미리 숫자로 정하지 않고, 정상 구간 창들에서 나온 값의 분포(예: 상위 1% 분위수)로 정한다. 이렇게 하면 오탐이 얼마나 날지 미리 조절할 수 있다.

**시간 창:** 기본 5분. 비교 변수로 15분 창, 요청 N건 단위 창을 함께 실험한다.

**저하 시작 시점 추정:** 판정과 함께 `estimated_start`(창 단위)를 반환해 `incidents.estimated_start`를 채운다. 원인 분석 에이전트가 변경 시점과 비교하는 근거다.

## 결과

**긍정적**

- 비교 실험이 과제 C(탐지 지연–오탐률 상충 관계)의 연구 결과물로 직접 이어진다.
- 인터페이스 분리로 `AI-MDL`이 구현체를 완성하기 전에도 `AI-SVC`가 더미 구현체로 스케줄러를 완성할 수 있다.
- 임베딩 모델이 바뀌면 이전 임베딩과 거리 비교가 무의미해지므로, 임베딩 모델 버전을 `evaluations`에 함께 기록해 불일치를 감지할 수 있다.

**부정적**

- 3가지 구현체를 모두 작성해야 하므로 `AI-MDL` 구현 비용이 늘어난다.
- 5분 창 약 150건에서 KS 검정의 검정력이 작은 저하에 충분한지 사전 확인이 필요하다.

**후속 작업**

- 구현체 3개 + 오프라인 평가 코드 작성 (11/11까지, SP2 일정)
- `DriftDetector` 인터페이스 확정 (`docs/specs/interfaces.md`, T3-01, 10/28까지)
- 5분 창 약 150건에서 KS 검정 검정력 확인 (미결 사항)
- SP3 실험 후 기본 방식 수치를 이 ADR에 기록하고 상태를 갱신

## 옵션별 장단점

### 옵션 1 — 고정 임계값 단독

- 장점: 가장 단순하고 설명이 쉽다.
- 단점: 분포 모양 변화를 못 잡고, 임계값 설정 근거가 약하다.

### 옵션 2 — 통계 검정 단독

- 장점: 분포 전체를 비교하고 p-value로 근거를 제시한다.
- 단점: 임베딩 같은 다차원 데이터에 직접 적용이 어렵다.

### 옵션 3 — 3방식 교체 가능 구현체 (채택)

- 장점: 비교 실험이 연구 결과물이 되고, 실험 후 최적 방식으로 기본값을 설정할 수 있다.
- 단점: 구현 비용이 단독 방식보다 크다.
