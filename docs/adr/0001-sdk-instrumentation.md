# ADR-001: 앱 내부 맥락을 기록하기 위해 프록시 대신 SDK 방식으로 계측한다

| 항목 | 값 |
| --- | --- |
| **상태** | 수락됨 |
| **날짜** | 2026-10-14 |
| **작성자** | `AI-SVC` |
| **검토자** | `AI-MDL` |

## 컨텍스트

이 플랫폼이 답하려는 질문은 "품질이 떨어졌는가"가 아니라 "**어떤 버전에서** 떨어졌는가"이다. 따라서 요청 기록에는 토큰·비용·지연뿐 아니라 그 요청이 사용한 프롬프트·모델·검색 설정 버전과 RAG 내부 단계(검색 → 프롬프트 조립 → 생성)가 함께 남아야 한다. LLM 관측 도구의 수집 방식은 크게 프록시 방식(Base URL을 교체해 호출을 중계)과 SDK 방식(앱 코드에 계측 삽입)으로 나뉘며, 어느 쪽을 택하느냐가 기록 가능한 정보의 범위를 결정한다.

## 결정 근거

- 앱 내부 맥락(프롬프트·검색 설정 버전, RAG 단계별 스팬) 기록 가능 여부 — 이 프로젝트의 핵심 기능과 직결된다.
- 감시 대상 서비스의 가용성에 주는 영향 — 관측이 장애 원인이 되면 안 된다.
- 도입 비용(사용자가 감수해야 하는 코드 변경량).
- 표준 준수 여부와 도구 종속성.

## 고려한 옵션들

- 옵션 1: 프록시 방식 (Helicone 류, Base URL 교체)
- 옵션 2: SDK 방식 (Langfuse·Phoenix 류, 데코레이터·컨텍스트 매니저 삽입)
- 옵션 3: 혼합 방식 (프록시로 기본 수집 + SDK로 버전 정보 보강)

## 결정

옵션 2 **SDK 방식**을 선택한다. 이 프로젝트의 핵심 산출물인 "원인 변경 지목"이 성립하려면 요청마다 앱 내부의 버전 묶음과 RAG 단계별 스팬이 반드시 남아야 하는데, 프록시는 LLM 호출 경계 바깥을 볼 수 없어 이를 구조적으로 기록할 수 없다. 수집 실패가 서비스 응답을 막지 않아야 한다는 비기능 요구도 프록시 구조로는 보장할 수 없다. 혼합 방식은 두 경로의 기록을 사후에 합쳐야 해 복잡도만 늘고 얻는 것이 없다.

## 결과

**긍정적**

- 프롬프트·모델·검색 설정 버전을 요청 단위로 정확히 연결할 수 있어 원인 분석 에이전트(ADR-007)의 근거 데이터가 확보된다.
- 검색·재순위 등 RAG 내부 단계를 개별 스팬으로 남겨 저하 지점을 단계 수준에서 좁힐 수 있다.
- 비동기 배치 전송(BatchSpanProcessor)을 쓰므로 수집 경로 장애가 사용자 응답을 막지 않는다.

**부정적**

- 사용자가 자신의 코드에 데코레이터를 넣어야 해 도입 장벽이 프록시보다 높다.
- 언어·프레임워크별 SDK가 필요하다. 이번 범위는 Python 하나로 한정한다.

**후속 작업**

- `src/sdk/`에 데코레이터와 `VersionContext` 구현 (T1-01, T1-02)
- 계측 적용/미적용 p95 지연 차이 측정 절차 수립 (T1-04 인수 기준)
- SDK 사용 가이드(README) 작성

## 옵션별 장단점

### 옵션 1 — 프록시 방식

- 장점: Base URL 한 줄만 바꾸면 되어 도입 비용이 사실상 0이다.
- 장점: 감시 대상의 언어·프레임워크에 무관하게 동작한다.
- 단점: 앱 내부 맥락을 볼 수 없어 헤더로 수동 전달하지 않는 한 버전 추적이 불가능하다.
- 단점: 프록시가 요청 경로에 들어가므로 프록시 장애가 곧 서비스 장애가 된다.

### 옵션 2 — SDK 방식 (채택)

- 장점: 버전·검색 설정·단계별 스팬 등 앱 내부 맥락을 원하는 위치에서 정확히 기록한다.
- 장점: 비동기 내보내기라 수집 실패가 서비스 응답에 영향을 주지 않는다.
- 단점: 사용자 코드 수정이 필요하고, 언어별 SDK를 따로 만들어야 한다.

### 옵션 3 — 혼합 방식

- 장점: 도입 초기에는 프록시만으로도 기본 지표를 볼 수 있다.
- 단점: 같은 요청이 두 경로로 들어와 중복 제거·식별자 정합 문제가 생기고, 8주 일정에서 감당할 복잡도가 아니다.
